# 第 25 课：分析埋点契约与 A/B 实验

**目标：** 从游戏问题设计遥测事件、漏斗和实验，并看清 CCGS 分析师的隐私、决策与实现边界。

完成本课后，你应该能：

1. 从要回答的设计问题推导事件名、用途、属性和触发条件。
2. 为 A/B 测试写出假设、玩家分组、稳定分配、成功指标、样本量和运行时长。
3. 发现并发实验的玩家分组重叠，说明为什么它会让结果难以归因。
4. 将埋点设计、游戏代码接线、数据隐私和设计决策分配给正确责任方。

## 问题

新手教程的完成率下降了。团队想知道玩家在哪一步离开，并测试提示文案是否有帮助。仅仅加一个 `tutorial_completed` 事件够不够？还要定义漏斗、事件属性、实验分配、成功指标、数据保留和上线后验证。本课沿 CCGS 的 `analytics-engineer` Agent 追踪这些合同。

## 从问题到事件合同

分析师先阅读现有设计、规范和标准，列出已有约束与未决问题；在草拟之前要询问数据要回答什么问题、哪些同意和保留规则适用、遇到未定义情况如何处理。发现既有 schema 冲突时先指出，不能默默切换命名规则。

一份可接线的事件定义至少要回答：

- **用途：** 这个事件回答哪个产品问题？每个事件都要有文档化目的。
- **名称：** Agent 建议 `[category].[action].[detail]`，例如 `tutorial.step.started`、`economy.currency.spent`。项目已有命名合同优先；Agent 测试规范明确要求发现并报告冲突。
- **属性：** 哪些字段构成漏斗和分析所需的最小数据集？每项都应有含义和类型；不能为了“以后也许有用”而无限收集。
- **触发条件：** 具体在什么状态转换或玩家动作发生时发出，避免同一事件在重试、重进或界面重绘时重复计数。
- **漏斗：** 指出每一步由哪个事件标记，区分开始、完成和中途离开，才能解释转化或流失位置。

分析师给程序员的是接线规格（事件名、属性、触发条件和隐私/退出约束），不是 GDScript、C# 或 Unreal 代码。数据可以提供证据和建议，但不能单独替游戏设计师决定是否上线某项设计。

## A/B 实验与上线验证

`analytics-engineer` 的实验设计要求覆盖完整要素：

1. 写出可检验的**假设**，说明哪个版本会改变哪个行为，以及预期方向。
2. 定义**玩家分组**和**指标**，说明分配单位。变体按玩家稳定分配，不能每次会话重新随机。
3. 预先规定**最低样本量**和**最短运行时间**，避免看了一点数据就下结论。
4. 并发实验使用互斥玩家分组。实验窗口和玩家段重叠时，结果可能被两个改动共同影响；可改为先后运行、分成互斥群组，或在确实要研究交互时设计需要更大样本的 factorial 实验。

分析仪表盘也要写清每张图的指标来源和能触发的行动。到了 `/team-release`，职责从“提出指标和埋点”转为“在发布构建上验证事件确实触发、仪表盘确实收到数据、关键漏斗已接线”；这是签核证据，不是实验结果本身。

隐私规则必须由项目资料与负责者给出。快照要求只收集必要数据，对可选收集提供退出/同意路径，遥测身份应匿名或假名化，隐私政策列出数据和保留时间。值未确定时先标为待定，不能由分析师或练习脚本自行补出合规结论。

## 实践：审阅事件和实验样例

运行：

~~~sh
python3 learn_claude_code_game_studios/practice/audit_analytics_contract.py
~~~

练习读取 `practice/fixtures/s25_analytics_contract.json` 和 `s25_sample_events.ndjson`。校验器会检查事件命名、用途、触发条件、日志中缺少或未定义的事件/属性、待定的同意与保留字段、A/B 测试的稳定分配和样本/时长参数，以及相同玩家段上重叠的实验窗口。

样例故意包含一个缺少必需属性的教程完成事件、一个未登记的事件、一个潜在直接标识属性、两项在相同新玩家段重叠的实验，以及未决的同意/保留规则。它们是需要复核的发现，不代表系统自动判定法律合规或实验失败。你可以修改 JSON/NDJSON 后重跑；脚本始终只读输入，不修改项目文件。

随后将 `studio-tests/agents/operations/analytics-engineer.md` 中的冲突案例与当前 schema 对照：若原项目用 snake_case，不能一边保留一边又新增 dot notation。再手工把已批准的事件设计映射到 UX 规格的接线表，给程序员说明精确触发点。

## 本课结论

遥测设计是一份产品问题、事件语义、实验条件、数据治理和代码接线之间的合同。分析师定义和验证合同；程序员按合同接线；安全角色协助隐私审查；游戏设计师根据数据与目标共同作决定。只有预先说明数据如何产生、谁会被比较、结果如何判定，仪表盘上的数字才有解释空间。

## 简化说明

- 课程校验器是本课新增的教学脚本，不属于 CCGS。CCGS Agent 测试规格本身注明没有自动 runner，需人工审阅或通过 `/skill-test` 观察 Agent 行为。
- 合成日志不连接游戏、SDK、玩家账号、数据库或线上仪表盘，不代表真实埋点已接线。
- 事件/属性检查仅做结构验证；脚本对 `email` 等字段的提示只是敏感字段线索，不是完整 PII 检测器。
- 样例实验的日期窗口与同名分组只是练习输入。真实实验需要数据负责人确认分组定义、样本需求、统计方法和项目隐私政策。
- CCGS 1.2.0 快照及其团队规模配置为本课证据范围；使用不同版本前要复核 Agent 和 orchestration Skill。

## 自测

1. 为什么一个事件必须写用途与触发条件，而不能只写名称和一组属性？
2. 为什么 A/B 变体需要按玩家稳定分配，而不是按每次会话重新随机？
3. 两项实验并发且覆盖相同玩家段时，哪些结论会受到混淆？可以怎样调整？
4. 项目没有给出同意或保留规则时，分析师应继续补默认值吗？
5. `/team-live-ops` 的分析计划与 `/team-release` 的遥测签核分别验证什么？
6. 为什么数据增加不能单独决定是否发布某项玩法或 UI 改动？

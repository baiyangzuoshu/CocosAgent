# Claude Code Game Studios 课程大纲

## 课程目标

以 `engine/Claude-Code-Game-Studios/` 中的 CCGS 1.2.0 快照为依据，沿项目入口、Agent、Skill、配置、自动化和质量系统逐层阅读，建立对该模板实际边界的理解。

## 实现与阅读约定

- 每课放在独立的 `sNN_主题/` 目录，以 Markdown 保留问题、文件位置、观察步骤、结果和简化说明。
- CCGS 不是可运行的游戏引擎。本课程不复制它的 Agent/Skill 文件，也不以模拟调用冒充 Claude Code 的实际运行证据。
- 结论优先由本地快照的配置、脚本、合同和文档交叉核对；README 的宣传性概述不能单独证明运行行为。
- 当前课程主题是静态源码阅读和流程追踪；如果以后加入可运行练习，单独记录其依赖和验证范围。

## 课程路径

| 课 | 主题 | 主要源码对照 | 阶段结果 |
| --- | --- | --- | --- |
| 0 | 仓库地图与系统边界 | `README.md`、`CLAUDE.md`、`project.yaml`、`.claude/settings.json`、`studio-tests/README.md` | 画出组成模块并指出 CCGS 与游戏本体、Creator 的边界 |
| 1 | 会话入口与上下文装配 | `CLAUDE.md`、`.claude/docs/`、`.claude/settings.json` | 解释哪些规则随会话加载、哪些资料按需读取、哪些 Hook 由事件触发 |
| 2 | Agent 分层与跨域协调 | `.claude/agents/`、`.claude/docs/agent-roster.md`、`.claude/docs/coordination-rules.md` | 按职责追踪一次纵向委派和冲突升级 |
| 3 | Skill 与工作流合同 | `.claude/skills/`、Skill 下的 `CONTRACT.md` / `references/`、`.claude/docs/skills-reference.md` | 从用户命令找到入口 Skill、依赖资料和产物 |
| 4 | 项目配置、严谨度与自动化模式 | `project.yaml`、`.claude/docs/effects-map.md`、`workflow-modes.md`、`automation-modes.md` | 区分 rigor 对流程重量的影响与 automation 对询问方式的影响 |
| 5 | Hooks、Rules 与安全边界 | `.claude/settings.json`、`.claude/hooks/`、`.claude/rules/` | 把自动事件检查与按路径加载的编码规则区分开 |
| 6 | 游戏开发阶段与 Gate | `docs/WORKFLOW-GUIDE.md`、`.claude/docs/workflow-catalog.yaml`、`.claude/skills/gate-check/` | 把阶段、产物和门禁连成可追踪的流程图 |
| 7 | Story 从准备到完成 | `/create-stories`、`/story-readiness`、`/dev-story`、`/story-done` 的 Skill 与合同 | 追踪一个 Story 的输入、执行、证据和关闭条件 |
| 8 | 运行观察与 QA 证据 | `.claude/docs/run-and-observe.md`、QA Skills、`production/qa/evidence/` 约定 | 说明测试通过、构建成功、实机观察分别证明什么 |
| 9 | CCGS 如何测试和升级自身 | `studio-tests/`、`UPGRADING.md`、`CHANGELOG.md` | 读懂框架测试覆盖面和升级时需保护的项目数据 |

## 第一课：仓库入口

从[第 0 课](s00_repository_map/README.md)开始。先区分“用来组织开发的模板”和“模板将来帮助制作的游戏”，再用文件清单核对 README 声称的模块数量与目录结构。

## 边界

CCGS 的主文档和本地源码可能随上游版本变化。每课引用本地路径和版本；如果版本标记不一致，先更新观察结果，不把旧快照结论直接外推。

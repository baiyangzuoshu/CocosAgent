# Cocos Creator Agent CLI

Standalone local CLI for Cocos Creator 2.4.15 projects. It can run without Codex, Claude Code, or the retired Creator-native CocosAgent. The package owns the stdio MCP server, native Codex/Claude MCP setup, bundled Creator Skills and installer, loopback bridge, Creator project extension template, and canonical Creator command contract.

## Requirements

The current source version is 0.12.34. On macOS, `creator installations` discovers Creator `.app` bundles in the standard Cocos install locations; `project open` can select the unique installation matching the project's Creator version when `--creator` is omitted. Opening waits by default for a live extension handshake and a successful `creator.project.info` round trip, so `editorReady: true` confirms the selected path and Creator version answered from the editor. It reuses an already-open matching project and reports ambiguous or incompatible instances without launching another copy. After a readiness timeout, macOS Accessibility is queried for Creator modal dialogs; if permission or the query is unavailable, the result says so rather than guessing. The bundled Creator extension is 0.8.24. Existing scene nodes support approved transform, active-state, rename, reparent, Button click-event, component-property, component-addition, component-removal, and subtree-deletion changes, alongside AssetDB-backed asset operations, all with precondition checks and disk readback recovery. Scene composition can instantiate an exact AssetDB Prefab as a new scene node; `creator.prefab.source.inspect` reads the exact saved Prefab and `.meta` by AssetDB UUID and reports a bounded node/component summary. `creator.prefab.instance.inspect` reads the exact live scene instance, its linked Prefab root and bounded descendant links, plus saved scene/Prefab hashes. `creator.prefab.instance.override.plan/commit/reconcile` invoke Creator's native Apply or Revert action after native approval and bind the exact live instance state plus saved scene/Prefab hashes. They report an observed effect only after the expected AssetDB file changes are read back; they do not claim component-by-component override equivalence and must be accepted in Creator 2.4.15. `creator.prefab.source.patch.plan/commit/reconcile` provide a constrained existing-Prefab edit path through Creator Prefab edit mode; the live capability is advertised only when the scene process exposes `curMode`, `save`, and `pop`. This path still needs real Creator 2.4.15 save/exit/reopen acceptance. `creator.editor.eval` and `creator.editor.eval-file` add native-approved, bounded execution for inline scripts or exact project `packages/*/editor-scripts/*.js` files; scripts run with Creator `Editor` privileges and are not sandboxed. Their results do not verify arbitrary effects or persistence, and reconciliation never reruns them. Every supported scene-node write now confirms persistence only after rereading the exact AssetDB `.fire` and `.meta` files and verifying the planned node, component, or subtree state. `sceneSaveCompletionConfirmed` remains false because Creator 2.4.15 documents no acknowledgement for its scene save IPC. `vcs status` adds a read-only Git summary grouped by scenes, Prefabs, scripts, assets, metadata, project settings, and other files, including `.meta` pairing hints for changed assets.

- Node.js 20 or newer.
- Cocos Creator 2.4.15 for editor-connected commands.

## Install and update

The CLI distribution channel is a versioned GitHub Release tarball, not the public npm registry. The first matching Release must be published before these commands work. Install an exact release globally with:

```sh
VERSION=0.12.27
npm install --global "https://github.com/baiyangzuoshu/CocosAgent/releases/download/cocos-creator-agent-cli-v${VERSION}/cocos-creator-agent-cli-v${VERSION}.tgz"
```

Check for or install the latest release from the terminal:

```sh
cocos-creator-agent self-update --check
cocos-creator-agent self-update
```

Pin or roll back to a specific release with `cocos-creator-agent self-update --version <VERSION>`. Updates download the release archive and its SHA-256 asset, verify the checksum, then ask npm to replace the global package. Verify the installed package with `cocos-creator-agent version --format json`.

For a private GitHub repository, the updater reads `GH_TOKEN` or `GITHUB_TOKEN`, then falls back to `gh auth token --hostname github.com`. The token is sent only to `api.github.com`; authenticated asset downloads use GitHub's release-asset API and follow its signed download redirect. Never put the token on the command line.

Repository maintainers publish a CLI release by updating `package.json`, committing the change, and pushing a matching `cocos-creator-agent-cli-v<VERSION>` tag. The GitHub Actions workflow checks the tag against the package version, creates an npm tarball, and attaches the archive and SHA-256 file to the GitHub Release. Bump `creator-extension/package.json` whenever its installed behavior or contract changes; extension updates use the template bundled in the installed CLI.

`doctor` is read-only and does not start the bridge. It checks the Node.js and bundled contract versions, bridge health, connected Creator instances, and—when `--project-root` is supplied—the project extension and path identity.

`vcs doctor` is a separate read-only Git/filesystem diagnostic. It requires the exact Git repository root and a Creator project root inside it; it does not stage, rewrite, or restore files. It reports tracked `library/`, `temp/`, `local/`, or `build/` paths, missing or orphaned asset `.meta` sidecars, duplicate main/subasset UUIDs parsed from JSON metadata, and paired Git conflict markers in bounded text files. Findings are diagnostic evidence, not an AssetDB import receipt; symlinks are not followed and scan limits are included in the JSON result.

`vcs status --git-root <absolute-path> --project-root <absolute-path>` reads Git's working-tree and index status, then groups changes by Cocos scenes, Prefabs, scripts, assets, metadata, project settings, and other files. It includes branch/upstream counts, staged versus unstaged state, changes outside the selected Creator project, and missing/orphaned `.meta` pairing hints for changed assets. It is read-only; `vcs doctor` remains the full project integrity scan.

`vcs diff --git-root <absolute-path> --project-root <absolute-path> --path assets/Scenes/Level.fire [--from <revision>] [--to <revision>]` compares a Creator 2.4.15 `.fire` scene or `.prefab` between Git revisions or from `HEAD` to the working tree. It matches nodes by serialized UUID and reports hierarchy, transforms, component additions/removals, and serialized component property changes. Linked Prefab scene changes stay attributed to the instance node; the command does not infer which source Prefab field caused an override. The command reads Git blobs and regular project files only, and rejects unsupported asset identity, malformed serialization, symlink paths, and oversized files.

`vcs blame --git-root <absolute-path> --project-root <absolute-path> --path assets/Scenes/Level.fire --node <node-uuid> [--revision <revision>] [--max-commits 128]` finds the newest first-parent commit that changed the selected serialized node UUID. It includes author, commit subject, and the semantic node/component change, and reports when the requested history limit was reached. It is read-only, refuses shallow clones, follows the asset path without rename tracking, and reports component changes with their owning node.

`vcs conflicts --git-root <absolute-path> --project-root <absolute-path>` reads unmerged Git index stages and explains Creator `.fire`/`.prefab` conflicts by node UUID. It compares base-to-ours and base-to-theirs changes, separates overlapping fields from disjoint or convergent changes, and reports metadata identity mismatches. This is an explanation only: Git stages and working files remain unchanged, and the result explicitly says manual resolution is still required.

`instances list` also reports recent authenticated but incompatible extension handshakes under `rejectedInstances`, including the extension-reported project path and mismatch reasons. These diagnostic records have no command session or capabilities. `doctor` flags them as errors instead of reporting only zero instances.

`creator installations` reports discovered bundle paths, Creator versions, executable availability, and whether each installation matches the supported 2.4.15 contract. By default it scans `/Applications/Cocos/Creator`, `/Applications/CocosCreator`, their matching per-user `~/Applications` locations, and direct Cocos-named entries under `/Applications`; `--search-root` scans one additional absolute directory to depth two. Discovery is read-only and follows no symlinks. On unsupported platforms, use an explicit Creator path where its package format is supported.

`project open` first validates the absolute project path and `project.json` Creator version. Before it opens or switches a project, verify the project name, absolute path, Creator version, and current open state in Cocos Dashboard. Pass `--creator` to select an exact macOS Creator `.app`; if omitted, the CLI discovers the unique installation matching the project version and fails on zero or multiple matches. By default, it checks for an existing matching instance, launches Creator only when none is connected, and waits up to 120 seconds for the extension handshake plus a read-only `creator.project.info` response whose project path and Creator version match. On timeout, it uses the Creator process ID from the extension handshake (or the launched process ID) to query macOS Accessibility for `AXDialog`/`AXSheet` windows. The response distinguishes a detected modal dialog, no detected dialog, and a diagnostic that is unavailable; it never treats missing Accessibility permission as proof that no dialog exists. A timeout returns nonzero with `editorReady: false`. Use `--no-wait-ready` only when you need the earlier process-launch behavior. `--format json` returns structured errors on stdout for machine callers.

Use `cocos-creator-agent help <command> [<subcommand>]` or append `--help` to a command to show focused usage; `help search <query>` searches CLI usage and the Creator command catalog. Machine callers can use `--json` or `--format json` on errors. Error objects include `schemaVersion`, stable `error.code`, `error.kind`, and `exitCode`. Exit codes are `1` for general failures, `2` for usage or input errors, `3` for bridge/MCP connection failures, `4` for Creator/project/build workflow failures, `5` for write conflicts or required reconciliation, and `10` when a Creator preview or project test fails.

## MCP and Agent Skills

The CLI starts its own stdio MCP server with `cocos-creator-agent mcp serve`. Use `mcp configure codex` or `mcp configure claude-code` to register that server through the corresponding client CLI; `--dry-run` previews the change and the command writes only the `cocos-creator-agent` entry. Codex MCP configuration is user-scoped. Claude Code uses user scope by default and `--local` for the current project. Existing same-name configurations are checked first; a different configuration is preserved and reported unless `--force` is provided. Use `mcp status <client>` and `mcp remove <client>` to inspect or remove the managed entry. Restart the Host after setup.

The npm release bundles all Creator workflow Skills and Creator 2.4.15 reference notes. `skill show [name]` reads the bundled instructions without installing them; `skill show --list` lists them. `skill install <client>` installs all bundled Skills into Codex `~/.codex/skills/` or Claude Code `~/.claude/skills/`; `--local` uses `.agents/skills/` for Codex or `.claude/skills/` for Claude Code. Use `--skill <name>` to select one, `--dry-run` to preview, and `skill refresh <client>` to update previously managed copies. The installer preserves unrelated files, detects edits, and refuses unmanaged or modified targets by default. `--force` backs up the replaced directory under `~/.cocos-creator-agent/skill-backups/`. Reference notes are installed beside the client skill directory so relative links continue to resolve.

Use `instances list` to discover an editor instance, then pass its exact ID to `capabilities` or `call`. The Creator catalog includes read commands and script-asset write workflows:

1. Call `creator.script.create.plan` with an existing `assets/` subfolder, an `assets/`-relative JS/TS path, and exact source. Creator verifies that the parent path has no symlinks and the file and `.meta` are absent, then stores a private operation record under `~/.cocos-creator-agent/creator-operations/` and returns an operation ID, plan hash, source preview, and recovery conditions. It does not change project assets or create folders.
2. After reviewing that plan, call `creator.script.create.commit` with only its operation ID and plan hash. Creator opens a native approval dialog showing the target and exact source. Cancel makes no project change. Approval triggers a fresh project/version/path/absence/hash check, then creates the asset through `Editor.assetdb.create`.
3. The extension reads the created script and `.meta` back through the same Creator instance and returns the UUID, importer, source hash, metadata hash, and conditional recovery data. If the response is lost or the bridge restarts, call `creator.script.create.reconcile` with the original operation ID. Writes are never automatically retried; a changed target is reported as a conflict.

For an existing asset, read it first and pass its exact `sourceSha256` to `creator.script.modify.plan` with the complete replacement source. The plan binds the asset path, AssetDB UUID/importer, source and `.meta` hashes, and stores the prior source outside the project. Commit requires the operation ID and plan hash plus Creator's native approval; it rechecks all preconditions immediately before writing through `Editor.assetdb.saveExists`, then reads the source and AssetDB identity back. `.meta` is preserved. On uncertainty, call `creator.script.modify.reconcile`; never replay the write. After modification, `creator.script.recompile.plan` binds a follow-up AssetDB refresh to the exact script UUID, source hash, importer, and `.meta` hash. Its approved commit calls Creator's documented `Editor.assetdb.refresh` and returns `passed` only when the callback includes that exact script and no `asset-db:script-import-failed` event was observed. An import failure is returned with diagnostics; an empty/ambiguous refresh result stays `unconfirmed`. The operation never edits source and never reruns during reconciliation.

The scene-node read command can inspect one node by scene UUID and node UUID even when it is outside the bounded snapshot. `creator.scene.compose.plan` prepares up to 12 new nodes, transforms, 24 registered components, typed scalar or asset properties, and 12 Button click handlers as one exact operation. A node may specify `prefabUuid` to instantiate that exact AssetDB Prefab; its root transform must provide all eight transform fields, and the operation does not add components or bind Button events on the Prefab root. Existing nodes can serve as parents or event targets, but this operation does not mutate them. It rejects unregistered classes, implicit component requirements, unsupported properties, duplicate child names, stale targets, unknown asset UUIDs, and missing handler methods. `creator.scene.compose.commit` shows the full plan in Creator's native approval dialog, rechecks the scene, resource, and Prefab identities, applies through Creator Scene Script, requests `scene:stash-and-save`, and verifies node UUIDs, hierarchy, transforms, component properties, resource UUIDs, PrefabInfo links, and click-event handlers in same-session readback and from the exact serialized `.fire` plus `.meta` files. It reports `completed` only if the files semantically match the plan. Creator 2.4 documents no completion acknowledgement for the save IPC, so `sceneSaveCompletionConfirmed` remains false even when `scenePersistenceConfirmed` is true. After interruption, `creator.scene.compose.reconcile` only observes and classifies state; it never retries the write. A `save-required` or `save-unconfirmed` result means disk persistence was not verified, so inspect and save manually in Creator before reconciling. `creator.prefab.source.inspect` reads an exact AssetDB Prefab's saved source and `.meta` by `prefabUuid`; pass `nodeUuid` to focus the bounded response on one node. It verifies UUID/importer identity and node/component references, but reports disk state only; unsaved Prefab edit-mode changes are outside this readback. `creator.prefab.source.patch.plan` accepts one node's explicit `before`/`after` diff for node name, active state, 2D position/scale, Sprite enabled/SpriteFrame, or Label enabled. It also supports `action: compensate` or `action: replay` by deriving the inverse from a completed `sourceOperationId`. Commit requires native Creator approval, rechecks source/meta hashes and node identity, changes only the live Prefab edit-mode object, waits for the save callback and `scene:saved`, exits and reopens the same Prefab, then checks the live node and exact disk `.prefab`/`.meta` again. Reconciliation observes state and never replays writes. Adding/removing Prefab components, arbitrary serialized fields, and applying or reverting scene-instance overrides are outside this command. The edit-mode sequence has not yet had real Creator 2.4.15 runtime acceptance.
`creator.prefab.instance.inspect` takes `sceneUuid` and `nodeUuid`. It reports whether the selected node belongs to a linked Prefab instance, the exact instance root and Prefab UUID, bounded descendant links and component identities, and the saved scene/Prefab hashes. `creator.prefab.instance.override.plan` takes the same identifiers plus `action: "apply"` or `"revert"`; it requires the instance to exist in the saved scene and freezes the live instance state plus scene/Prefab source and `.meta` hashes. Commit shows the exact target and action in a Creator-native approval dialog, rechecks every bound identity, invokes `scene:apply-prefab` or `scene:revert-prefab` for the resolved instance root, and requests a scene save. Apply reports `effect-observed` only when the exact Prefab source changes without `.meta` identity drift. Revert requires both the live instance state and exact saved `.fire` to change while the linked Prefab source remains unchanged. The result does not decode every component override or prove field-by-field equivalence with the Prefab source; inspect the result in Creator. Creator 2.4.15 runtime acceptance is still required. Reconciliation reads state only and never repeats the native action.

The generic `creator.editor.eval.plan` freezes inline JavaScript and optional JSON input; `creator.editor.eval-file.plan` instead reads a `.js` file under a project package's `editor-scripts/` directory. Review the complete plan, then call the matching `.commit` with its operation ID and plan hash to open Creator's native approval dialog. Both modes execute trusted code with the Creator `Editor` API and are not a sandbox. Script effects and persistence are not verified; time limits are best-effort and do not guarantee termination or cancel side effects. On timeout or interruption, call the matching `.reconcile`, inspect the project manually, and never replay the operation. Example inline plan input is `{"source":"return { version: Editor.version, value: input.value };","input":{"value":7}}`.

`creator.scene.node.rename.plan`, `.commit`, and `.reconcile` rename one existing node by exact scene/node UUID. The plan binds the original path, parent UUID, name, requested sibling-unique name, Creator instance, contract version, and exact saved-scene baseline. Commit requires native Creator approval, rechecks live and disk state before applying, requests scene save, and reports `scenePersistenceConfirmed: true` only after the exact saved `.fire` node UUID, name, parent, path, active state, and transform read back as expected. Reconciliation compares both editor memory and disk and reports `save-required` when memory changed but the file did not; it never repeats the rename. Creator's save IPC still has no documented completion acknowledgement.

`creator.scene.node.delete.plan`, `.commit`, and `.reconcile` remove one exact non-root node and its descendant subtree. The plan binds the scene/node UUID, original path/name, parent UUID, and a bounded ordered snapshot of every descendant's UUID, name, parent, and child count (maximum 256 nodes); larger subtrees are refused. Commit requires native Creator approval, rechecks the full live and saved snapshot, detaches and destroys the node through the Creator scene API, requests scene save, and confirms that every subtree UUID is absent from the exact saved `.fire` file. `creator.scene.node.remove-component.plan`, `.commit`, and `.reconcile` remove one exact registered component by its serialized instance ID and refuse a component required by another component. Component addition similarly binds the saved component identity set and confirms the new instance ID and serialized class on disk. All three operations account for Creator's deferred destruction and never replay a write during reconciliation; if memory changed but disk did not, reconciliation reports `save-required` for a manual save. Receipts report disk persistence separately from Creator's unacknowledged save request.

`creator.scene.node.reparent.plan`, `.commit`, and `.reconcile` move one existing node under an exact target-parent UUID. The plan rejects root movement, cycles, no-ops, and sibling-name collisions, and binds the exact saved-scene baseline; commit rechecks both live and disk state before using Creator's `node.parent` setter. Local transform values stay the same, so world position can change; hierarchy changes can also invoke component lifecycle callbacks. The Creator approval dialog describes both effects. Completion requires the saved `.fire` node UUID, name, parent, path, active state, and transform to read back as expected. Reconciliation compares memory and disk and reports `save-required` if the scene file remains unchanged; it never repeats the reparent.

The single-node `creator.scene.node.set-active` operation changes an existing node's active state. Like transform, rename, and reparent, it binds the exact saved `.fire`/`.meta` baseline and confirms persistence only when the serialized node identity, hierarchy, active state, and transform match the expected after-state. `creator.scene.node.set-transform.plan` changes selected existing node fields among `x`, `y`, `z`, `scaleX`, `scaleY`, `angle`, `width`, `height`, `anchorX`, and `anchorY`; the plan records the selected fields' exact live before-values and binds them to the exact saved `.fire`/`.meta` hashes and serialized node state. Commit requires the operation ID and plan hash, opens a native Creator approval dialog, rechecks project/editor/contract and both live and disk before-state, applies through Creator Scene Script, requests scene save, and reads the same node back from memory and the exact AssetDB `.fire` file. `scenePersistenceConfirmed` becomes true only when the serialized node UUID, path, active state, and all transform fields match the expected after-state. `sceneSaveCompletionConfirmed` remains false because the IPC has no documented acknowledgement. Reconciliation observes both memory and disk; if memory changed but the saved scene did not, it reports `save-required` and never retries the write.

The component-add write slice adds one registered Cocos component class to one existing scene node. The plan resolves the class from Creator's loaded class registry and rejects unregistered/non-component classes, duplicate instances, and classes with implicit `requireComponent` dependencies. Commit shows the project, scene, node, and class in the native Creator approval dialog, rechecks the saved component identity set, adds one component through `Node.addComponent`, requests scene save, and confirms that the returned component instance ID and serialized class are present in the exact saved `.fire` file. Component constructors and lifecycle hooks are project code and may run; the dialog names this risk before the write. Reconciliation never replays the add. If memory changed but disk did not, it reports `save-required`; if the Creator session changed, manual review is required.

The existing-node component-property write slice changes one declared public property on one exact component instance. It supports scalars; typed `Vec2`/`Vec3`/`Vec4`/`Size`/`Rect`/`Color`; bounded arrays of supported primitives, typed values, node refs, or component refs; exact active-scene `cc.Node` and component-instance references; and exact AssetDB references to SpriteFrame, Texture2D, AudioClip, Prefab, BitmapFont, or TTFFont. Plans require the public property to be serializable and present on the saved component, and bind the exact AssetDB `.fire`/`.meta` hashes, persistent component ID, serialized class ID, owning node, and saved property value. Commit rechecks live and disk state after approval; `scenePersistenceConfirmed` requires semantic readback of the saved property, including typed values, ordered arrays, resource UUIDs, node UUIDs, and component IDs/classes/owning nodes. If only memory changed, reconciliation reports `save-required`; after a manual save it observes the result without replaying the setter. A changed Creator session still requires manual review. Values are checked against Creator's declared property metadata and exact scene identities; arbitrary project objects, asset-reference arrays, inherited fields, internal names, stale before-values, unsupported resource types, and component queries exceeding the 32-instance bound are refused. Resource references are loaded by UUID and checked for exact class and identity before assignment. Component constructors and property setters are project code and may have side effects. `creator.scene.button-events.set.plan|commit|reconcile` replaces the full click-event list on one exact Button instance, verifies each target node and registered handler, binds the unique serialized `cc.Button` and exact saved event list from `.fire`/`.meta`, and shows the complete before/after list for approval. Completion requires the serialized target UUIDs, component names, handlers, and custom event data to match on disk; otherwise the operation reports `save-required` when memory changed but the saved file did not. Reconciliation observes live and disk state without replaying the event write.

`creator.asset.import.plan` and `creator.asset.import.commit` import one selected external file into an existing `assets/` folder through `Editor.assetdb.create`. The plan binds the source bytes by SHA-256 and requires an absent destination; the approved commit verifies Creator's generated `.meta` UUID and AssetDB row. Only regular files up to 32 MiB with a matching filename extension are accepted. `creator.asset.move.plan`, `.commit`, and `.reconcile` move or rename one existing file asset through `Editor.assetdb.move`; the plan binds its UUID, bytes, `.meta`, importer, and type, requires an existing destination folder with no file or metadata collision, and only permits keeping the same extension. Asset moves and deletion are limited to 128 MiB files so identity hashes remain bounded. Commit checks move preconditions again after approval and verifies the old path is absent and the exact asset identity and bytes exist at the destination. Reconciliation observes both paths and never repeats the move. `asset references --instance <id> --uuid <asset-uuid>` scans bounded text files under `assets/` for an exact AssetDB UUID and reports whether the scan was complete; the target asset and its `.meta` are excluded, binary formats are skipped, and an incomplete scan cannot establish that the asset has no references. `creator.asset.delete.plan`, `.commit`, and `.reconcile` delete one exact main file asset through `Editor.assetdb.delete` only when the complete bounded scan finds no incoming text-file references. Sub-assets, assets with sub-assets, incomplete scans, and stale reference state are refused. Deletion is permanent from this CLI and does not create a backup; review the plan and project backup before approving. `creator.asset.import-settings.plan`, `.commit`, and `.reconcile` update only the allowlisted Creator 2.4 texture fields `wrapMode`, `filterMode`, `premultiplyAlpha`, `genMipmaps`, and `packable` on one PNG/JPEG asset. The operation binds the exact AssetDB UUID, source hash, prior `.meta` hash and full metadata object, requires native Creator approval, saves through `Editor.assetdb.saveMeta`, preserves other metadata, and verifies the complete result; uncertain saves are reconciled without replay. Creator may reimport the texture. `creator.prefab.create.plan` and `.commit` ask the Creator Scene panel to serialize one exact active-scene node as a Prefab, then verify the generated serialization, `.meta`, and AssetDB identity; Prefab data is never hand-edited. `scene diff --before <snapshot.json> --after <snapshot.json>` compares bounded snapshots by stable node UUID and reports hierarchy, transform, component-property, resource-reference, and Button-event changes. These Creator-side write paths still require Creator 2.4.15 editor acceptance.

Script creation and modification change script assets only and do not attach components or verify runtime behavior. Use the explicit recompile operation for import/compile feedback; use a Creator build and preview test for project-wide build and runtime evidence. The explicit `extension install` command writes the bundled extension into the selected project's `packages/cocos-creator-agent-extension/` directory and refuses to overwrite an existing extension. `extension status` reports its version and tracked-file drift. `extension update` and `extension uninstall` refuse to overwrite or remove locally changed/unmanaged files by default. Pass `--force` only after reviewing the report; the CLI preserves the existing extension under `~/.cocos-creator-agent/extension-backups/` before replacing or removing it. Reload the project in Creator after install, update, or uninstall.

`creator build` and `creator compile` wrap the documented Creator 2.4.15 [`--build` and `--compile` command line](https://docs.cocos.com/creator/2.4/manual/zh/publish/publish-in-command-line.html) and return JSON with the selected project, Creator patch, platform, output path, process exit result, success flag, failure code/reason, elapsed time, and bounded logs. Do not rely on process exit code alone: Creator Builder can log `Build Failed:` and still exit with code 0. The CLI returns `CREATOR_BUILD_REPORTED_FAILURE` with the parsed reason and reports success only when no failure is detected and output exists. Pass the exact Creator 2.4.15 application bundle and absolute project path. By default, build outputs go to a unique path under `~/.cocos-creator-agent/builds/`; a requested build output path must be new and outside the project. The CLI does not clean or overwrite build output. `creator compile` requires an existing native build output directory from a prior build and operates on that directory. `--auto-compile` is accepted only for native `creator build`. Web builds need no external platform SDK. Native workflows check for the configured Android SDK/JDK or Xcode before starting; missing requirements are reported without launching Creator. This initial workflow verifies macOS `.app` bundle metadata; other Creator package formats need their own version reader before use.

`creator test --instance <id> --session <id>` runs a same-session preview smoke test: it calls `creator.preview.interact` with bounded actions/assertions and exits nonzero when any assertion fails. `creator test --project-root <path>` runs suites declared in `.cocos-agent/tests.json`; the project runner supports Node, approved Creator Provider, direct Creator Editor script, and exact preview-session adapters, and writes JSON/JUnit reports. Editor scripts run from `packages/*/editor-scripts/*.js` after Creator native approval and are not sandboxed. Pass `--rerun-failed <previous-results.json>` to rerun suites that failed in an earlier report; the project root and test manifest hash must still match, and this always creates a new report. For Node suites, `--shard <index>/<total>` partitions test cases for parallel workers (Node 20.5+); Creator Provider, direct Editor script, and preview suites are assigned whole to one deterministic shard. `--coverage` adds Node line/branch/function coverage and, for preview suites, Chromium V8 function and block-range coverage for scripts served by the selected preview origin (Node 20.1+). Preview coverage reports source offsets, not line coverage; Creator Provider and direct Editor script coverage are unsupported. It is project-configured test orchestration, not a built-in Creator unit-test framework. `creator watch` supports both explicit-file preview smoke tests and affected project-plan suites; it emits newline-delimited JSON events and stops on Ctrl+C/SIGTERM. Paths stay inside the exact connected project and remain subject to the documented file/count/size bounds. Creator 2.4.15 has no documented built-in Unity-style `test` CLI command.

## Project tool registrations

A project may add `.cocos-agent/tools.json` to register named aliases for commands already present in the shared Creator contract. Read and plan commands can be exposed directly; write or control commands are accepted only when the canonical command requires Creator approval. The registry cannot run project callbacks or change a command input schema. MCP ignores project-provided titles and descriptions when publishing tool definitions, and write aliases retain destructive annotations and the native Creator approval flow. The registry is re-read from the selected live Creator project for listing and invocation; calls include its SHA-256 so edits invalidate stale tool discovery.

```json
{
  "schemaVersion": 1,
  "tools": [
    {
      "id": "player-script",
      "title": "Read player script",
      "description": "Read the player's component script and Creator metadata identity.",
      "commandId": "creator.script.read"
    }
  ]
}
```

Use `project-tools list --instance <id>` to discover the declarations and `project-tools call --instance <id> --tool player-script --input '{"scriptPath":"assets/Scripts/Player.ts"}'` to invoke one. Aliases use the mapped built-in command's exact input schema, access level, approval requirement, and live Creator capability. Pass `--registry-hash <sha256>` when invoking a tool discovered earlier; the call is rejected if the project declaration changed. This is declarative routing over canonical commands, not an arbitrary Editor code execution API.

## Asynchronous tasks and recovery

`tasks start` returns a durable task ID without waiting for the Creator operation. `tasks wait --id <id> --after-sequence <N> [--wait-ms 25000]` holds a local bridge request until a newer persisted event arrives or returns the current progress on timeout. The response includes `eventSequence`; pass that cursor to wait for the next update. `tasks list` returns bounded summaries and `tasks status` reads one task's result; global `tasks list` works while Creator is disconnected, and `--instance <id>` filters it. `tasks cancel` requests cooperative cancellation. Task records are stored under `~/.cocos-creator-agent/tasks/` with restrictive permissions and contain the exact input for explicit recovery, while status output omits the raw input and reports its SHA-256.

After a bridge restart, queued tasks become interrupted; dispatched reads can be explicitly resumed. A dispatched script-creation commit resumes through `creator.script.create.reconcile`; scene-node transform, rename, reparent, deletion, component add/removal, active-state, and property commits resume through their matching `creator.scene.node.*.reconcile` command, each with its original operation ID and never by replaying the write. Other dispatched plans, writes, and controls become `needs-reconciliation` and are not replayed automatically. Cancellation is best effort after dispatch; a potentially side-effecting command may require reconciliation even when cancellation was requested.

## Compile and Web preview feedback

`diagnostics read --instance <id>` reads Creator Builder compile events, script-import failures, and editor Console events with a sequence cursor. A `compile-finished` event proves only that the event fired; it is not by itself a successful compile result.

`preview start --instance <id> [--port 7456]` requests Creator's active-scene Web preview and requires a native Creator approval. Creator's selected preview target must be Browser; the documented IPC follows that selection. Creator opens its normal preview, then the local bridge opens an isolated Chromium session to the same loopback port. The command returns a `previewSessionId` bound to that Creator instance, project, and scene UUID. Select Chromium with `COCOS_CREATOR_AGENT_BROWSER` when it is not in a standard install location.

Use that session ID with `preview observe`, `preview screenshot`, `preview refresh`, `preview interact`, and `preview stop`. Interactions are limited to a keyboard whitelist with bounded press duration, normalized canvas clicks, and declarative scene/node/Console/component-field assertions. Refresh reuses the same browser session and verifies the expected scene again. Screenshots are saved under `~/.cocos-creator-agent/captures/`; stopping closes the Agent-owned browser but leaves Creator's preview server running.

The runtime browser commands fail closed when Chromium, the loopback preview server, or the expected scene identity is unavailable. Runtime evidence is not inferred from source code or from Creator compile events.

# 第 5 课：如何按任务、能力、延迟和成本选择模型

**目标：** 能把具体需求转成模型选择标准，并用同一组任务比较候选模型，而不是靠记型号或只看单价。

## 本课问题

“能力最强的模型”是不是每个功能的最佳选择？如何判断更轻量、更快的模型是否已经够用？

## 前置知识

- [第 2 课](../s02_text_generation_flow/README.md)：模型根据输入生成输出。
- [第 3 课](../s03_tokens_context_window/README.md)：Token 数量和上下文限制会影响请求规模。
- [第 4 课](../s04_prompt_instructions_roles/README.md)：Prompt 影响任务要求是否清楚。

## 官方资料

- [Model selection](https://developers.openai.com/api/docs/guides/model-selection)：从任务出发比较模型和推理设置，并用相同输入做实验。
- [Models](https://developers.openai.com/api/docs/models)：查询当前模型的能力、输入模态、工具、上下文窗口和限制。
- [Pricing](https://developers.openai.com/api/docs/pricing)：核对当前输入、输出和缓存 Token 价格及工具费用。
- [Reasoning models](https://developers.openai.com/api/docs/guides/reasoning)：了解推理能力与 reasoning effort 对速度、Token 用量和质量的影响。
- [Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization)：了解模型、生成长度和请求设计对响应时间的影响。

## 1. 先写清楚要解决的任务

先描述“模型要做什么”，再查模型目录。至少确认：

- 任务是简单生成、分类、提取，还是复杂分析、规划或多步决策？
- 输入会包含文本、图片、音频等哪些内容？需要哪些工具或输出能力？
- 什么结果算合格？哪些事实、格式或准确性要求必须满足？
- 用户要等多久？功能调用频率和预算大概是多少？

如果模型不支持所需输入模态、工具或上下文长度，即使它在其他任务上很强，也不适合这个功能。可在官方[模型目录](https://developers.openai.com/api/docs/models)核对各模型当前能力和限制。

## 2. 把需求变成可检查的门槛

| 维度 | 先问什么 | 可观察的指标 |
| --- | --- | --- |
| 能力与质量 | 能否完成这个具体任务？ | 正确率、事实保持、格式通过率、人工验收率 |
| 延迟 | 用户最多能等多久？ | 首个可见结果时间、完整响应时间、p50/p95 |
| 成本 | 这个功能会调用多少次、每次处理多少内容？ | 每请求费用、每个成功任务费用、月度总量 |
| 适配性 | 是否支持需要的上下文、模态和工具？ | 对照模型页核对能力与限制 |

把可接受的质量、延迟和成本门槛先写下来。否则只看到“答案更好”或“单价更低”，无法判断改动是否真的适合产品。

## 3. 用任务类型缩小候选范围

- **范围清楚、经常调用的任务：** 先试成本和延迟更低的候选模型，检查它能否稳定过质量门槛。
- **含糊、多步骤或需要规划的任务：** 把具备相应推理能力的模型列入候选，并测量额外推理带来的质量收益和时间、费用变化。
- **实时交互：** 优先验证完整响应时间和首个可见结果时间；减少不需要的输出长度和推理工作也可能改善等待时间。
- **图片、音频或工具工作流：** 先确认模型支持所需模态和工具，再比较质量、速度和费用。

这些是筛选方向，不是固定的型号对照表。模型能力、可用工具和设置会变化；同一模型的 reasoning effort 等参数也可能影响速度、质量和 Token 用量，且支持值因模型而异。[Reasoning models](https://developers.openai.com/api/docs/guides/reasoning)、[Models](https://developers.openai.com/api/docs/models)

## 4. 做一次公平比较

1. 收集一组有代表性的真实任务，包含常见情况和容易失败的情况。
2. 为每种任务写验收标准，例如“保留角色名和地点”“不补充未提供的剧情事实”“只输出一句台词”。
3. 先固定输入、Prompt 和其他设置，用同一批任务请求不同候选模型。
4. 记录质量、完整响应时间、输出 Token 和费用；对于需要人工修正的任务，也记录修正工作量。
5. 选择满足质量和延迟门槛的低成本方案。之后再固定模型和输入，单独试不同推理设置。

OpenAI 的模型选择指南建议用相同输入做对比，在多种代表性任务上检查结果，并把审阅或修复时间也算进完成时间；目标是保留能够达到质量标准的最轻量配置。[Model selection](https://developers.openai.com/api/docs/guides/model-selection)

## NPC 对话的比较表

假设游戏需要生成 NPC 招呼语。先定义验收要求：保留给定的 NPC 与场景信息、不添加新设定、语气合适、时延不超过产品目标。再用同一组玩家输入比较候选模型：

| 候选 | 质量门槛是否通过 | p95 完整响应时间 | 每次成功调用成本 | 是否满足产品目标 |
| --- | --- | --- | --- | --- |
| 候选 A | 待测 | 待测 | 待测 | 待测 |
| 候选 B | 待测 | 待测 | 待测 | 待测 |

若候选 A 成本更低但经常漏掉场景约束，它不算合适；若候选 B 质量更高但超出交互等待要求，也不一定适合实时招呼语。可以为复杂剧情分析另做一组任务，用不同门槛选择候选。

## 5. 理解“每 Token 单价”和“每个成功任务成本”

文本请求的费用可先粗略理解为：

```text
输入 Token 用量 × 输入单价
+ 输出 Token 用量 × 输出单价
+（若使用）工具或其他计费项
```

单价、缓存价格和工具费用以当前[官方定价页](https://developers.openai.com/api/docs/pricing)为准。推理模型产生的推理 Token 会计入生成用量；不同模型处理同一文本时的 Token 数和生成长度也可能不同。所以更便宜的每 Token 单价不一定代表更便宜的单次任务。重复调用次数、失败重试和人工修正也会影响总成本。[Reasoning models](https://developers.openai.com/api/docs/guides/reasoning)、[Pricing](https://developers.openai.com/api/docs/pricing)

## 本课检查

完成本课后，能做到：

- 先按任务能力、输入模态、工具和上下文要求筛选候选。
- 为质量、延迟和成本写出可检查的门槛。
- 用同一组代表性任务比较候选模型，并计算每个成功任务的成本。
- 选出满足质量标准、速度目标和预算的轻量方案，并知道何时需要更强模型。

## 练习

为以下两个游戏任务各写一条候选选择标准，并说明你会记录哪三项比较结果：

1. 每次玩家进村时生成一句简短招呼语，每分钟会被大量调用。
2. 玩家卡关时，需要结合多条任务线索判断下一步该做什么。

不要先填具体模型名称。先写清任务、质量门槛、等待时间和预算，再决定要比较哪些候选。

## 简化与边界

- 模型名称、价格、上下文、工具支持和默认设置会变；在选型时查[当前模型目录](https://developers.openai.com/api/docs/models)和[定价页](https://developers.openai.com/api/docs/pricing)，不要照抄课程中的旧型号或旧价格。
- 模型选择指南给出的是起点，不是保证。真实结果取决于任务、Prompt、输入长度、输出长度、推理设置和服务环境。
- Token 单价不是全部成本；工具费用、缓存、失败重试和人工复核都可能改变每个成功任务的总成本。
- 本课只讲选型方法，不展开 API 请求、批处理、流式输出或生产路由策略；这些会在后续课程继续学习。

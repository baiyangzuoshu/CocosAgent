# 第 26 课：什么样的系统才需要 Agent？

**目标：** 能区分一次模型调用、固定流程与 Agent；能根据任务中的多步决策、工具使用和不确定情况，判断是否值得让模型控制工作流。

## 本课问题

## 1. 能使用模型，不等于 Agent

普通模型调用通常是：应用发送输入，模型生成答案，应用把答案交给用户。模型即使能理解自然语言，也不一定负责整个任务的流程。

OpenAI 的实践指南把 Agent 描述为能够代表用户独立完成任务的系统：LLM 参与控制工作流、根据状态作出决定，并能使用工具从外部系统读取信息或采取行动。单轮问答、简单聊天机器人或只做情绪分类的模型应用，如果模型不控制工作流执行，就不因此成为 Agent。[A practical guide to building agents](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-agents/)

这里的“独立”有明确边界：Agent 只能使用被授予的工具和权限，应有完成条件；遇到错误、缺少信息或高风险操作时，可以停止并交给用户处理。它不表示系统可以无限制地自行行动。

| 系统形态 | 谁决定下一步 | 例子 |
| --- | --- | --- |
| 一次模型调用 | 应用固定调用模型一次 | 把一封邮件概括成三句话 |
| 固定程序流程 | 代码按预先写好的步骤与规则推进 | 读取 CSV，校验字段，然后按固定公式汇总 |
| 带工具的单次回答 | 模型可提出一次工具请求，应用执行后返回答案 | 搜索一页最新资料并总结结果 |
| Agent 工作流 | 模型根据当前结果决定继续、选工具、询问用户、完成或停止 | 分析故障描述，查询状态，选择诊断步骤，再根据结果处理或升级 |

## 2. 看任务本身，而不是看产品名称

OpenAI 建议先找传统确定性规则难以稳定处理的工作流。常见信号有：

- **判断复杂：** 需要结合上下文、例外情况和多条信息作判断。
- **规则难维护：** 规则数量很多、分支频繁变化，继续堆规则容易出错。
- **依赖非结构化输入：** 需要理解自然语言、文档或对话中表达的意图和信息。
- **后续动作取决于结果：** 需要查询外部数据、选择下一项操作，并检查操作是否成功。

这些信号说明 Agent 可能有用，但并不能证明必须采用 Agent。先确认任务需要这种灵活性，而且能定义权限、完成条件和质量检查；否则，确定性程序可能更简单、更容易验证。[A practical guide to building agents](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-agents/)

## 3. 用五个问题做初步判断

1. **步骤是否固定？** 输入到输出的步骤完全明确时，优先考虑普通程序。
2. **判断是否固定？** 如果规则稳定、所有分支可枚举，程序中的条件逻辑通常够用。
3. **下一步是否要看中间结果？** 如果需要读取结果，再据此选择不同工具、补问信息或调整路径，模型控制流程可能有价值。
4. **是否需要多次行动并核对结果？** 多步工具使用、失败后的有限恢复或转交，是 Agent 常见工作流特征。
5. **能否安全地限制和验收？** 工具权限、停止条件、人工审批和结果质量必须可以检查。

| 判断结果 | 常见选择 |
| --- | --- |
| 步骤与规则稳定，输入输出明确 | 确定性程序 |
| 需要模型理解或生成，但流程只有一次 | 普通模型调用，必要时用结构化输出 |
| 一次回答需要补充外部信息或调用一次工具 | 带工具的模型请求 |
| 需要根据中间结果反复作出受限决策，并有明确停止或转交条件 | Agent 候选；先从一个 Agent 和少量工具开始 |

**工具本身不是判断标准。** 一个应用可以只调用一次 Web Search 或函数，然后结束；这仍可能只是普通模型请求。关键在于模型是否承担了工作流中的连续决策，以及系统是否需要依据任务状态继续推进。[Agents](https://developers.openai.com/api/docs/guides/agents) · [A practical guide to building agents](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-agents/)

## 4. 例子：处理客户退款请求

假设用户用一段文字描述问题。系统可以按固定规则处理完全标准的申请；如果信息缺失，可能要追问；遇到复杂描述时，可能要查订单、阅读政策，再判断下一步。若退款动作会改变账户余额，还要先检查权限，并在需要时向人审批。

```text
收到问题
   ↓
判断是否缺信息 ── 是 → 向用户追问 → 根据回答继续判断
   ↓ 否
读取订单和相关政策
   ↓
检查结果是否足以处理 ── 否 → 停止并转交人工
   ↓ 是
给出处理建议；如需实际退款，再经过授权/审批
   ↓
检查结果并结束
```

如果“判断缺什么、查什么、是否可以处理”会随对话和查询结果变化，这个流程是 Agent 候选。如果所有条件和分支都稳定、只需按规则做相同处理，直接写成程序可能更合适。高影响的写操作应独立设置权限与审批，不应因为模型判断“看起来合理”就自动执行。

## 本课检查

完成本课后，能解释：

- 使用 LLM 或工具，不会自动让一个应用成为 Agent。
- Agent 的关键特征是 LLM 参与控制工作流、按当前状态选择受限动作，并能结束或交还任务。
- 复杂判断、难维护的规则和非结构化输入是 Agent 值得评估的信号；它们本身不是充分理由。
- 单次工具调用可以属于普通模型请求；是否是 Agent，要看模型是否控制多步工作流。
- 设计 Agent 时必须定义工具权限、停止条件、结果核验和必要的人工审批。

**自测：** “给模型启用 Web Search”就一定构成 Agent 吗？如果搜索一次、总结结果后立即返回，通常不必称为 Agent；如果模型还要按搜索结果选择后续步骤并检查任务是否完成，则更符合 Agent 工作流的特征。

## 简化与边界

- 本课只判断 Agent 是否适合某个任务，不实现 Agent，也不比较 API、SDK 和产品入口；入口选择是第 27 课。
- “多步”是常见工作流特征，不是靠步骤数量定义 Agent。关键是模型是否控制工作流执行，并能根据状态作出决策。
- Agent 可能出错或误用工具。上线前需要代表性样本、质量评估、运行边界和相应的人类监督；本课不展开护栏与评估实现。
- 本课没有安装 SDK、连接工具或发送真实 API 请求。

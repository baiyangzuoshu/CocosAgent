# CocosAgent 真实项目驱动开发计划

制定日期：2026-10-10。状态：已确认开发方向；第 0 步中插件技能包已安装验收，MCP 工具目录与 Creator 扩展仍待实际对齐。适用版本：Cocos Creator 2.4.15。

## 1. 目标与产品路径

让用户在真实游戏工程中提出开发需求，Agent 理解项目约定，调用正确的编辑器能力完成修改，通过编译、日志、运行状态、画面和磁盘读回确认结果，交付可审阅的变更与证据。失败时说明执行到了哪里，并依据已记录的副作用完成恢复。

近期主路径为：

```text
用户任务
  → 外部 coding agent（模型、代码搜索/编辑、对话）
  → CocosAgent 插件与按需 skills
  → MCP / 现有 Host（合同、目标、回执、恢复）
  → Creator 2.4.15 扩展（编辑器操作与观察）
  → 真实游戏项目及其运行结果
```

Unity 参考为[官方 Agent 插件](https://github.com/Unity-Technologies/unity-agent-plugin)、[CLI/MCP 集成](https://github.com/Unity-Technologies/skills/blob/main/skills/unity-cli/references/integration-advanced.md)和[运行验证流程](https://github.com/Unity-Technologies/skills/blob/main/skills/unity-cli/references/playmode-verification-loop.md)。Creator 的具体接口、资源格式和公开行为继续核对[2.4 官方手册](https://docs.cocos.com/creator/2.4/manual/zh/)、本地源码与实际运行结果。

当前缺口与范围取舍依据[产品审核](cocos-agent-unity-product-audit-2026-10-10.md)。招聘要求作为能力与案例的映射参考，由项目实践产生对应成果。

## 2. 当前基线与待确认信息

2026-10-10 审核快照：Creator 实例 `ready`、14 个能力条目；压力合同 0.2 已报告 available。工作区新 MCP 服务发现 42 个工具，本会话原有 39 个工具和旧压力输入；仓库插件原有 6 个 skills，已安装插件缓存只有 1 个。Prefab 源检查可用，源编辑为 `PREFAB_EDIT_MODE_API_UNAVAILABLE`。随后完成 MCP/Host/扩展版本指纹诊断与逐命令合同校验。插件 0.3.0 现已安装并启用，11 个 task skills、29 份随包引用均已逐项核验；真实 MCP stdio 发现/读取了 skill index、技能及引用。活动 MCP Host 未重启，工具目录仍是旧版；Creator 扩展版本/指纹仍待加载新代码后实测，状态与下一动作见[运行时合同对齐记录](cocos-agent-runtime-contract-alignment-0.2.md)。这些数量和状态只用于定位本轮问题，后续重新实查。

已有场景、资源、构建、运行时、回执与恢复模块作为复用基础。技术示例与模拟测试证明的范围，按原合同和轨迹使用；Prefab 源编辑、跨 Bundle 新合同与压力合同 0.2 的完整运行验收继续标注其实际状态。

当前尚未确定独立真实项目的绝对路径及首个开发任务。第 0 步可以立即进行；第 1 步应从用户明确指定的工程与需求开始，不自行把研究示例认定为真实产品工程。

## 3. 开发顺序与验收门槛

| 步骤 | 核心交付 | 验收门槛 |
| --- | --- | --- |
| 0：实际加载版本对齐 | 插件、MCP、Host、扩展及所需 skills 的一致性诊断与更新流程 | 实际宿主发现的工具 schema 与 Creator 合同一致，必要 skills 可读；不兼容项有明确状态 |
| 1：真实项目与首个任务 | 独立工程接入、任务描述、项目约定与现有阻塞清单 | Agent 选中正确工程并读回上下文，形成范围明确、可以执行的任务计划 |
| 2：按阻塞补能力并完成任务 | 必要的命令、日志/编译反馈、预览与运行观察 | 用户目标完成，磁盘与运行结果匹配；失败或未观察项不得算成功 |
| 3：沉淀可复用 skill | 按需工作流、产品包内可读引用、分发与使用证据 | 真实宿主发现并读取该 skill，Agent 使用其步骤完成对应任务 |
| 4：持续项目验证 | 后续任务、缺口记录与可复现回归 | 同一项目连续修改仍正确，新增范围均能追溯到实际需求 |

### 第 0 步：版本、合同与 skill 分发对齐

先使现有能力可靠地到达用户实际使用的 Agent。

工作内容：

1. 定义可读取的组件版本与指纹视图，记录插件包、所需 skill 内容、MCP 工具 schema、Host 合同、Creator 扩展及当前实例身份。仅展示接线所需信息，密钥与认证令牌不进入诊断。
2. 对照实际宿主工具目录与 Creator 能力目录，修复本轮旧 MCP schema 和插件缓存缺失技能的分发问题。产品包版本随交付变化更新，避免长期用相同版本标识不同实现。
3. 对命令分别校验版本、schema、访问级别与实例身份，明确兼容、暂不可用和不兼容项。新命令未通过校验时禁止执行；基础查询不因可隔离的高级命令不兼容而丢失诊断入口。
4. 为实际更新过的命令收敛定义来源，减少 catalog、扩展和 MCP 的重复字段维护。按受影响命令逐步收敛，不把一次一致性修复扩展成全量架构迁移。
5. 通过宿主支持的更新/重载方式加载新实现，重新读回目录与指纹。`tools/list_changed` 适用于运行中实际注册目录的变化；源文件改动仍需要新代码加载，通知不能证明旧进程已更新。
6. 优先分发基础 skill 与当前任务所需技能。包内引用使用随包可达资源或经校验的依赖位置；研究资料按任务读取。外部宿主实际加载技能是本轮门槛，内置 Assistant 的按需技能读取按其使用需求再安排。

验收：实际外部 Agent 查询实例和能力；当前 Creator 2.4.15 目标及活动场景匹配；实际 MCP 输入可完整表达对应合同；所需 skill 由宿主读到正确版本。用隔离夹具验证版本不匹配、缺失技能与不兼容项的诊断，无未授权写入。只完成握手或内存传输测试不足以宣布本步骤通过。

### 第 1 步：接入独立真实项目并确定一个任务

接入用户明确指定的 Creator 2.4.15 游戏工程，使用项目真实目录、资源、脚本组件和开发约定。

工作内容：

1. 确认项目绝对路径、Creator 版本、当前引擎来源、启动场景/平台、活动编辑场景、Git 状态及现有未保存改动。目标选择继续使用显式项目注册与精确实例身份。
2. 提供最小的扩展安装/更新、Host 位置配置、项目注册和接线检查流程。更换目录或在研究仓库外打开项目后，仍能解析已安装 Host 与必要依赖。
3. 记录项目组织方式、节点/组件命名、资源与 Prefab 约定、已有代码入口、预览/构建方法。优先从现有文件和编辑器读取事实。
4. 选择一个小而完整的开发任务，例如修改现有界面的图标和交互，或修复一个具体的资源引用问题。最终选择以用户需求为准，不预先添加整套界面或玩法框架。
5. 建立任务记录：用户目标、受影响文件/对象、预期变化、当前状态、所需工具/skill、验收动作、失败恢复及明确未覆盖范围。

验收：外部 Agent 在该真实工程中完成一次只读检查，准确描述目标对象和必要约定，形成任务计划。无需复制示例场景、专用测试脚本或整套内容 release 才能接入。

### 第 2 步：按任务阻塞补操作与观察，完成首个开发任务

每次开发从任务中已经暴露的缺口出发。

| 任务阻塞 | 处理方式 | 成功证据 |
| --- | --- | --- |
| 找不到正确对象或引用 | 扩充必要的资产/场景查询与关联读取 | 返回项目内可校验的对象身份、类型及引用来源 |
| 现有节点/组件操作不足 | 增加该任务必需的受约束命令 | 预期差异、陈旧状态拒绝、保存读回及对应恢复验证 |
| 代码改动缺少编辑器反馈 | 将宿主代码编辑与 AssetDB/脚本导入、编译结果相接 | 修改后实际导入/编译状态及错误位置可读 |
| 无法确认游戏执行结果 | 暴露必要的预览、运行状态、日志和画面查询 | 精确目标、帧推进、画面与任务行为证据相互对应 |
| 任务需要普通项目构建 | 使用项目配置执行隔离输出构建并读取结果 | 构建退出状态、日志、输出身份及必要运行检查 |

实现约束：

- 编程 Agent 修改文本脚本；场景、Prefab 与资源导入继续经校验的 Creator 接口完成。保留已有回执、UUID、身份和陈旧状态检查。
- 命令名与参数在具体切片时确定，未实现的名称不登记为 available。只读命令应具有只读入口，例如已有 Prefab 源检查的可达性可在任务需要时补齐。
- 日志区分任务前已有错误与本次新增错误，并绑定来源项目和时间范围。编译未完成、日志不可读或观察缺失时明确返回等待/未观察状态。
- 预览观测关联实际场景、构建或会话；证明帧在推进后，再检查画面和目标行为。截图不单独作为游戏正常运行证据；磁盘读回不替代实际画面观察。
- 普通项目预览或构建直接采用本工程当前配置；只有任务涉及动态内容发布时，才使用已有 release、Bundle 与运行时替换流程。
- 不确定写入先查询原操作及磁盘/活动状态，禁止盲目重复写入。故障验证优先使用隔离夹具，真实工程中的既有改动按任务基线保护。

验收：从自然语言需求出发，真实外部 Agent 调用工具完成任务；记录实际工具、读回、日志、画面及任务行为。交付项目差异和验证结果。出现失败时，回执说明阶段与副作用，Agent 依据记录修复、补偿或准确停止；模拟调度和手工直调工具不能单独代替 Agent 任务验收。

### 第 3 步：在使用过程中沉淀与分发 skill

新增 skill 的触发条件：已有命令可以完成任务，但需要稳定、可复用的步骤、项目约定或版本特定的诊断知识；一个真实任务已经暴露并验证这些知识。

工作内容：

1. 先使用基础 skill 和已分发的对应任务 skill；需要新技能时，从该任务的成功步骤及失败恢复中提取。
2. 产品 skill 以 `plugins/cocos-agent-2x/skills/` 为权威发布源，包含触发条件、Creator 版本、必要输入、工具、验证动作、恢复方法、证据边界和必要引用。
3. 对同名文档副本进行按需收敛，研究笔记作为引用资料。避免让工具参数规则、能力状态和任务步骤在多处独立维护。
4. 验证插件安装/更新后宿主确实发现该技能、读取了必要引用；记录技能版本或内容指纹及实际使用证据。

验收：Agent 在明确任务中实际读取和使用该技能，结果由编辑器与运行验证支持。只有文件通过格式检查或提示词提到技能名，不算技能接入完成。

### 第 4 步：持续任务验证与后续取舍

在同一真实工程中继续用户需求，根据任务数据选择下一项：可能是 UI/Prefab、脚本与资源联动、引用修复、构建或性能排查。记录哪些现有能力已经足够、哪些缺口反复出现，再决定新增命令、技能或引擎改动。

验收关注连续修改后的层级、引用、Prefab 关系、脚本行为和运行结果；已有回归仅在变更影响它们或暴露具体风险时扩展。性能和原生专题由实际负载与设备需求触发；源码改造由可复现问题和同条件测量驱动。

## 4. 范围约束与每轮检查

- 当前只推进 2.4.15 产品实现；已有 3.x 研究与代码继续按历史证据使用，后续适配另行计划。
- 内置 Assistant、内容发布、Bundle 依赖、压力诊断和原生桥保留已有实现；其继续开发须关联实际任务阻塞。
- 每轮先核对：本轮用户目标、实际工程/实例、所需能力与 skill、已观察到的阻塞、成功证据和恢复方式。范围扩大时说明它解决哪一个当前问题。
- 新增工作记录其依据和验收状态；不要将本计划中的交付物写成现有能力。当前步骤的关键门槛未通过时继续处理该阻塞，独立可推进事项可以并行准备。
- 既有研究、招聘设计和历史开发路线作为背景资料；新增产品优先级以本计划及根目录 [AGENTS.md](../../AGENTS.md) 为准。

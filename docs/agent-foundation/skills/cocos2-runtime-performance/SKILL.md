# Creator 2.4 runtime performance diagnostic

Use this skill when an Agent needs to measure repeated runtime resource replacement and Sprite updates in a Creator 2.4.15 Web-Mobile build. It is a local screening run; it does not measure a physical phone, native memory, GPU memory, or production network conditions.

1. Call `cocos_2x_instances_get` and `cocos_2x_capabilities_list` for the registered project. Continue only when that exact instance is ready and `content.stress.run` is available. This command is 2.4.15 only.
2. Choose a completed, verified `web-mobile` build record and resource paths present in its built-in `resources` config. Contract 0.2 requires unique Texture UUIDs and PNGs at least 512×512 and 256 KiB. Keep `parseFixturePaths` separate from render-load `resourcePaths`; choose 2–16 packaged parser fixtures and one as `failureResourcePath` for the injected HTTP failure. Record dimensions, bit depth, color type, encoded bytes, UUIDs and SHA-256. The probe estimates uncompressed RGBA bytes as `width × height × 4`; this is not measured GPU, native or process memory.
3. Set workload and every budget explicitly. `profileId` is `macos-arm64-chrome-headless-swiftshader-1280x800`; `loadMode` is `cold-and-warm`; `budgetProfileId` is `macos-arm64-headless-swiftshader-host-screening-v1`. These name a Mac development host and SwiftShader screening profile, not a target device. For a starting local screen, use 96 replacement cycles, 512 temporary Sprite nodes, `packable: true`, 30 FPS, cold load P95 250 ms, warm load P95 20 ms, import/deserialize P95 50 ms, PNG parse P95 50 ms, synchronous release P95 8 ms and max estimated RGBA working set 64 MiB. These provisional thresholds need local calibration and are not product or release requirements.
4. Call `cocos_2x_content_stress_run` with `buildId`, `resourcePaths`, `parseFixturePaths`, `failureResourcePath`, `cycles`, `nodeCount`, `packable`, `profileId`, `loadMode`, `budgetProfileId` and all seven `budgets` fields. Contract 0.2 verifies cold cache misses, measures immediate warm loads and same-object identity, import and PNG parser callbacks, SpriteFrame creation/installation, node mutation, `EVENT_AFTER_DRAW` intervals, failed-load retention, reference balance, cache readback and cleanup. It writes a JSON trace and screenshots under `docs/agent-foundation/traces/`; the build, scene and release pointer remain unchanged.
5. Read the structured result and linked trace. Treat `acceptance.success` as the lifecycle/invariant gate and `budgetEvaluation.verdict` as the budget gate; a completed command can still report exceeded or unobserved metrics. Compare frame interval P95 against `1000 / targetFps`, cold/warm load and parser/release P95 against their named limits, and the peak estimated RGBA working set against `maxEstimatedRgbaWorkingSetBytes`. `likelyLoci` and `nextChecks` are investigation suggestions, not causal attribution. Check that owner reference deltas, failure retention and final cache readbacks are consistent.
6. Report the exact test rig, build, input textures, workload, budget verdict, and trace path. Separate measurement from inference. A headless SwiftShader pass is not a mobile frame-time acceptance. Do not change the scene, release selection, or build as part of this diagnostic.

The command contract and runner are documented in [`dynamic-content-pressure-2.4.md`](../../dynamic-content-pressure-2.4.md). The historical local Host run used two 128×128 flat-color stress textures already warm in the startup scene plus separate 2×2 parser/failure fixtures. It predates contract 0.2 and does not meet the current complex-PNG, cold-load or working-set requirements. The live MCP instance currently returns `CAPABILITY_CATALOG_INVALID`, so do not claim a real MCP/LLM stress run until the active extension catalog reports contract 0.2 as available. Historical two-pixel results verify probe mechanics only; they are not representative texture-load evidence.

# Creator 2.4 runtime performance diagnostic

Use this skill when an Agent needs to measure repeated runtime resource replacement and Sprite updates in a Creator 2.4.15 Web-Mobile build. It is a local screening run; it does not measure a physical phone, native memory, GPU memory, or production network conditions.

1. Call `cocos_2x_instances_get` and `cocos_2x_capabilities_list` for the registered project. Continue only when that exact instance is ready and `content.stress.run` is available. This command is 2.4.15 only.
2. Choose a completed, verified `web-mobile` build record and stress resource paths present in its built-in `resources` config. The runner requires unique PNG Texture UUIDs and source PNGs at least 64×64 pixels. Prefer the target game's representative atlases or textures and actual content dimensions; do not use tiny parser fixtures as render-load assets. Keep `parseFixturePaths` separate from `resourcePaths`; choose 2–16 packaged PNG fixtures, and choose one of them as `failureResourcePath` for the injected HTTP 503. Record dimensions, bytes, UUIDs, and hashes from the command output.
3. Set workload and every P95 budget explicitly. The supported profile is `macos-arm64-chrome-headless-swiftshader-1280x800`; it describes a Mac development host and software-rendered headless Chrome, not a target device. Use target-device budgets only when they have been measured and entered by the caller. For local screening, a starting profile is 96 replacement cycles, 512 temporary Sprite nodes, `packable: true`, and these provisional limits: 30 FPS, resource load P95 100 ms, import/deserialize P95 20 ms, PNG parse P95 20 ms, and synchronous release-call P95 8 ms. These limits are screening gates, not product requirements.
4. Call `cocos_2x_content_stress_run` once with all required fields: `buildId`, `resourcePaths`, `parseFixturePaths`, `failureResourcePath`, `cycles`, `nodeCount`, `packable`, `profileId`, and all five `budgets` fields. The run measures preloading, resource loads, import and PNG parser callbacks, SpriteFrame creation/installation, node position/scale mutation, `EVENT_AFTER_DRAW` intervals, failed-load retention, `refCount`, Asset Cache and Bundle Cache, and cleanup. It writes the diagnostic trace and screenshots under `docs/agent-foundation/traces/`, while leaving the build, scene and release pointer unchanged.
5. Read the structured result and linked trace. Treat `acceptance.success` as the gate result; a completed command can report an exceeded budget or failed invariant. Compare frame interval P95 against `1000 / targetFps`; compare each other P95 with its named limit. Check that owner reference deltas are one per release and final resource/cache readbacks are internally consistent.
6. Report the exact test rig, build, input textures, workload, budget verdict, and trace path. Separate measurement from inference. A headless SwiftShader pass is not a mobile frame-time acceptance. Do not change the scene, release selection, or build as part of this diagnostic.

The command contract and runner are documented in [`dynamic-content-pressure-2.4.md`](../../dynamic-content-pressure-2.4.md). The first local Host diagnostic run used two 128×128 flat-color stress textures (already warm in the startup scene) plus separate 2×2 parser/failure fixtures. It verified the report and lifecycle checks at 96 cycles and 512 nodes; the texture and parser costs are not representative of production assets. The current live MCP instance has not exposed or run this command yet. Historical two-pixel baselines are useful for checking the probe mechanics only; do not compare them as representative texture-load evidence.

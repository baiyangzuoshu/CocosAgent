2026-10-04 以[可复跑 Mac 探针](../probes/stage11-mac-storage.py)对两份历史包分别运行两次独立进程：首次 `before=null → setItem → after=临时值`，第二次 `before=临时值 → removeItem → after=null`。两版均测到 `isNative=true`、`isBrowser=false`、`window.localStorage` 为对象，且与公开 `sys.localStorage` 是同一对象。唯一临时键已删，生成的 2.4 `main.js` 与 3.8 `application.js` 均按原字节还原；3.8 应用容器内的临时结果文件也已清理，进程检查未发现探针实例。第一次默认沙箱运行中的 2.4 GUI 初始化受限，没有游戏脚本事件且文件已恢复，不算行为证据；上述有效轨迹来自可访问 Mac GUI 的执行环境。

后续还要在两版 Web 预览中做独立案例，并针对移动端、小游戏分别测试。现有 Mac 包均是历史构建快照；3.8 明确使用 Creator 安装包内置引擎，2.4 来源尚未确认，因此运行观察只代表对应包，不能当作邻接引擎改动的回归测试。skill 应保留版本入口、宿主边界和只删除临时键的清理规则。

同日以[可复跑回环 HTTP 探针](../probes/stage11-mac-http.py)对两版 Mac 包分别发送 200/503 请求，保留[2.4 业务 XHR](../traces/2.4.15-stage11-mac-native-http.jsonl)与[3.8 XHR/fetch](../traces/3.8.7-stage11-mac-native-http.jsonl)轨迹。2.4 和 3.8 的 XHR 对 503 仍触发 `onload`；3.8 的 `fetch` 对 503 仍 resolve。探针只访问 `127.0.0.1` 的临时服务，未触达外部服务器；生成脚本已逐字节恢复、临时结果文件已清理。此案例不能证明底层网络错误回调、资源管线下载、WebSocket 或其他平台。

同日以[连接被拒绝探针](../probes/stage11-mac-connection-refused.py)把 `127.0.0.1` 临时端口绑定但不监听，并重复执行两轮。2.4 的[XHR 轨迹](../traces/2.4.15-stage11-mac-native-connection-refused.jsonl)在 `timeout=4000` 下两次都是 `ontimeout`；3.8 的[XHR/fetch 轨迹](../traces/3.8.7-stage11-mac-native-connection-refused.jsonl)两次分别是 `onerror`/rejected。该探针同样逐字节恢复两份生成脚本并清理 3.8 临时输出。两轮输出一致，但 JSONL 保留最后一轮，不据此推断任意传输失败、TLS 或 Web 目标；尤其 2.4 的原生绑定源码不在本仓库。

再以[本机 WebSocket 回显探针](../probes/stage11-mac-websocket.py)对两版包运行，保留[2.4 客户端](../traces/2.4.15-stage11-mac-native-websocket.jsonl)、[2.4 服务器](../traces/2.4.15-stage11-mac-native-websocket-server.jsonl)、[3.8 客户端](../traces/3.8.7-stage11-mac-native-websocket.jsonl)和[3.8 服务器](../traces/3.8.7-stage11-mac-native-websocket-server.jsonl)。各轮均完成打开、文本回显与关闭，服务器收到了关闭码 1000。2.4 原生编译参数为 `USE_SOCKET=1`；3.8 构建配置包含 `websocket` 且 CMake 配置为 `USE_SOCKET ON`。客户端 2.4 `jsb.WebSocket=undefined` 而全局 `WebSocket=function`，3.8 两者均为函数。2.4 的关闭字段缺席；两版关闭回调当下 `readyState` 均在不同运行中变化，不作为稳定规则；3.8 事件记录 `code=1000/wasClean=true`。探针只访问 `127.0.0.1`，脚本 SHA-256 恢复一致，3.8 临时文件已清理。`wss://`、二进制、Web 与小游戏仍待单独验证。

同一探针的 `--drop-after-text` 模式在服务端收到文本后设置 `SO_LINGER` 重置 TCP，不发送 WebSocket Close 帧。两轮均产生[2.4 客户端](../traces/2.4.15-stage11-mac-native-websocket-abrupt.jsonl)/[服务器](../traces/2.4.15-stage11-mac-native-websocket-abrupt-server.jsonl)和[3.8 客户端](../traces/3.8.7-stage11-mac-native-websocket-abrupt.jsonl)/[服务器](../traces/3.8.7-stage11-mac-native-websocket-abrupt-server.jsonl)一致的 `open → close` 与握手→文本→TCP 重置序列；没有 `onerror` 或 `onmessage`。3.8 客户端 `close` 为 `1001/false`，2.4 关闭字段缺席。JSONL 保存第二轮；此结果只对应 Mac 已发布包及该受控断开位置。3.8 邻接 C++ 另有 `didFailWithError → onError → onClose` 分支，所以不能将“仅 onclose”写成所有故障规则。

同一探针的 `--binary-echo` 模式让两版包各发送五字节 `[0,1,127,128,255]`，并设置 `binaryType='arraybuffer'`。[2.4 客户端](../traces/2.4.15-stage11-mac-native-websocket-binary.jsonl)/[服务器](../traces/2.4.15-stage11-mac-native-websocket-binary-server.jsonl)与[3.8 客户端](../traces/3.8.7-stage11-mac-native-websocket-binary.jsonl)/[服务器](../traces/3.8.7-stage11-mac-native-websocket-binary-server.jsonl)均记录相同字节的二进制帧、ArrayBuffer 回调与正常关闭。这个单帧小样本不验证默认二进制类型、消息大小上限、分片、`wss://` 或 Web 平台。Web 预览地址 `127.0.0.1:7456/7457` 本轮均连接拒绝，尚无 Web 轨迹。

同一探针的 `--reject-handshake` 模式在服务端收到 Upgrade 请求后回 HTTP 403、不发送 101。两版各复跑两次，最后一轮[2.4 客户端](../traces/2.4.15-stage11-mac-native-websocket-rejected-handshake.jsonl)/[服务器](../traces/2.4.15-stage11-mac-native-websocket-rejected-handshake-server.jsonl)及[3.8 客户端](../traces/3.8.7-stage11-mac-native-websocket-rejected-handshake.jsonl)/[服务器](../traces/3.8.7-stage11-mac-native-websocket-rejected-handshake-server.jsonl)均显示客户端 `error → close`、服务端 HTTP 403、客户端从未 `open`。3.8 `close` 的 `code=0/wasClean=true` 是该包在失败握手下的观测，不可当作连接成功证据。Web 预览服务本轮仍未监听；桌面 UI 状态读取超时，未取得 Web 行为轨迹。

先用[热更新只读探针](../probes/stage11-mac-hotupdate-inventory.py)取得两版 Mac 包的 API 类型与当前 `FileUtils` 搜索路径，没有构造 `AssetsManager`。3.8 源码显示构造/加载本地 manifest 可能修改搜索路径甚至清理缓存，故纯诊断不得用创建管理器替代入口检查。两个示例均未检出 `.manifest`；2.4 `boot` 与 3.8 `onPostInitBase` 的采样阶段不同。后续行为实验只使用隔离的临时 manifest 和缓存。

另用[受控同版本探针](../probes/stage11-mac-hotupdate-check.py)分别在两包中构造管理器，以唯一临时目录存放本地 manifest/缓存，用回环服务提供同版本 `version.manifest`，仅调用 `checkUpdate()`。两版事件均为代码 `5 → 4`，搜索路径均在构造时前置临时 manifest 目录；[2.4 服务端](../traces/2.4.15-stage11-mac-native-hotupdate-check-server.jsonl)与[3.8 服务端](../traces/3.8.7-stage11-mac-native-hotupdate-check-server.jsonl)均只收到一次版本请求。尤其 3.8 的[包内轨迹](../traces/3.8.7-stage11-mac-native-hotupdate-check.jsonl)显示事件 4 时 `getState()=13`，但 JS 常量 `UP_TO_DATE=12/FAIL_TO_UPDATE=13`；邻接 C++ 状态枚举比 JS 多一个 `PREPARE_UPDATING`。这条错位规则要保留在 3.8 skill 中。探针恢复两包脚本的原 SHA-256，清理唯一临时目录；没有调用 `update()`，不验证下载、文件覆盖、重启或其他平台。

再运行同一探针的 `--remote-version 1.0.1` 分支。完整 manifest 含一个哨兵文件且服务端不提供其内容；两版[2.4 客户端](../traces/2.4.15-stage11-mac-native-hotupdate-new-version-check.jsonl)/[服务端](../traces/2.4.15-stage11-mac-native-hotupdate-new-version-check-server.jsonl)和[3.8 客户端](../traces/3.8.7-stage11-mac-native-hotupdate-new-version-check.jsonl)/[服务端](../traces/3.8.7-stage11-mac-native-hotupdate-new-version-check-server.jsonl)均给出 `version.manifest → project.manifest`、事件 `5 → 5 → 3`、无哨兵下载请求，临时目录保留 `project.manifest.temp`。2.4 代码 3 时状态 9 对应 `READY_TO_UPDATE`；3.8 状态 10 对应 C++ `READY_TO_UPDATE`，却被包内 JS 常量标为 `UPDATING`。`checkUpdate()` 未调用 `update()`；不能把这条路径升级成下载或重启成功规则。两份生成脚本与临时目录均已恢复/清理。

最后用 `--remote-version 1.0.1 --do-update` 在代码 3 回调调用 `update()`，回环服务仅提供单字节哨兵文件。两版[2.4 客户端与磁盘](../traces/2.4.15-stage11-mac-native-hotupdate-update.jsonl)/[服务端](../traces/2.4.15-stage11-mac-native-hotupdate-update-server.jsonl)、[3.8 客户端与磁盘](../traces/3.8.7-stage11-mac-native-hotupdate-update.jsonl)/[服务端](../traces/3.8.7-stage11-mac-native-hotupdate-update-server.jsonl)均记录 `5 → 5 → 3 → 5 → 5 → 6 → 8`，一个资产请求，缓存中的 manifest `1.0.1` 与资产字节 `41`，临时下载目录已清理。重新启动对应包后，管理器构造时从隔离缓存读到 `1.0.1` 并前置缓存目录，`checkUpdate()` 只请求版本文件后给代码 4。3.8 代码 8/4 时仍 `getState()=13`，要保留 JS/C++ 状态常量错位。此重启探针在宿主启动后注入管理器，不验证新版游戏脚本的启动前覆盖或 Bundle 刷新；错误重试/回滚、Android/iOS 和 Web 仍需分别验证。两份生成脚本均按原 SHA-256 恢复，唯一临时目录已删除。

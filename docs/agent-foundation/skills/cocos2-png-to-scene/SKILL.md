# Place a PNG Sprite in Creator 2.4.15

Use this skill for an authorized scene edit in a Creator 2.4.15 project. The public behavior is described by the [2.4 image asset manual](https://docs.cocos.com/creator/2.4/manual/zh/asset-workflow/sprite.html) and [Canvas manual](https://docs.cocos.com/creator/2.4/manual/zh/components/canvas.html): an image needs a SpriteFrame subasset for Sprite, and this bridge places its node under an existing Canvas. The version-specific implementation is `2.4.15NewProject/packages/cocos-agent-bridge/{main,scene}.js`; the Host contract is [operation.schema.json](../../../../tools/cocos-agent-bridge/operation.schema.json).

1. Confirm the exact project path and Creator version. From the repository root, run `node tools/cocos-agent-bridge/catalog-host.js --target "2.4.15=<absolute-project-path>" --query capabilities.list --project "<absolute-project-path>" --creator-version 2.4.15`. Require the returned instance's project path and `creatorVersion=2.4.15`, and `scene.pngSprite` with `contractVersion=0.1`, `access=write`, `input.required=[assetName,action]`, `status=available`, and `preconditions` including `canvasExisting`. If the scene changed, reopen the intended scene and refresh the catalog. If the intended scene lacks Canvas, stop with `CANVAS_NOT_FOUND`; this command does not create one. Do not infer Canvas from the truncated 30-node snapshot.
2. Confirm the active scene is the intended `.fire` file and contains the existing Canvas. For a new local PNG, run `bridge-host.js --project "<absolute-project-path>" --creator-version 2.4.15 --png "<absolute-png-path>"` to import it. Import alone does not place it in the scene. Check the generated `.meta` for an actual `sprite-frame` subasset; if absent, set the image's Type to Sprite in Creator and let the editor regenerate metadata. Do not handcraft a UUID or overwrite an existing resource. For an already imported PNG, use its filename in `assets/resources/`.
3. Run `node tools/cocos-agent-bridge/bridge-host.js --project "<absolute-project-path>" --creator-version 2.4.15 --scene-asset "<filename.png>" --scene-action apply`. The Host reads the SpriteFrame subasset UUID, performs version-specific preflight, writes under Canvas, saves, and verifies the `.fire` file plus a fresh scene snapshot. Capture the printed `operationId` and all `operation.receipt` lines. The result should identify the scene, node, SpriteFrame UUID, editor save result, and disk readback.
4. Run the same Host with `--operation-get "<operationId>"` to inspect the persisted six-phase state. `editor` and `disk` must be `passed` before reporting a saved scene edit. `preview=pending` remains pending until a real Creator/Web preview is observed and recorded for this operation. A prior preview of the same demo is not evidence for a new run.
5. On timeout, disconnect, `SCENE_SAVE_UNVERIFIED`, or a crash after the write intent, call `operation.get` and inspect the saved scene before deciding what to do. Never rerun the same ID; the Host rejects duplicate IDs. If the target node exists with a different SpriteFrame, stop at `SCENE_NODE_CONFLICT`. `compensate` is a new, identity-checked operation using the same filename and current scene; verify its own disk and recovery receipts. `INVALID_SCENE_SESSION` indicates a stale extension or mismatched session contract, so reload the matching package and refresh the catalog before another attempt. In this workspace, 2.4 Package Manager Reload has failed once; reopening the project restored the package.

Report the selected instance and scene, asset filename and SpriteFrame UUID, `operationId`, the six phase statuses, the exact saved-scene evidence, preview evidence or `pending`, and any unresolved side effect. The [operation contract note](../../cocos-agent-operation-contract-0.1.md) distinguishes durable disk recovery from scene compensation. The independent operation ID and interruption flow passed a localhost mock; a fresh 2.4 Creator interruption run is still required before claiming that failure path as editor-verified.

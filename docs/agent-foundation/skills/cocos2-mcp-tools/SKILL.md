# CocosAgent MCP tools for Creator 2.4

Use this skill when an MCP host exposes the `cocos_2x_*` tools. This adapter is fixed to Creator **2.4.15**; it cannot select Creator 3.8. Read the [MCP adapter contract](../../cocos-agent-mcp-0.1.md) for tool names, project allowlisting and transport setup. The MCP host supplies its model; CocosAgent does not need an LLM key.

Start with `cocos_2x_instances_list`. Select the exact project path returned by the tool, and require `state: ready`. Then call `cocos_2x_instances_get` or `cocos_2x_capabilities_list` for that `projectRoot`. Use only commands whose current catalog entry says `status: available`; the catalog includes `access`, preconditions, and the command input schema. Project paths and Creator version are constrained by the server process, so do not construct another target.

Call `cocos_2x_command_execute` with the selected `projectRoot`, catalog `command` ID, and matching `input`. The MCP tool schema has a separate input contract for every 2.4 command. Read-only commands such as `scene.snapshot` are safe for inspection. Other commands can import assets or change the active scene; for those, follow the corresponding version-specific skill and operation contract. Check the returned `success`, `outcome`, error code, phase receipts, and `operationId`. If the result is `needs-review`, call `cocos_2x_operation_get`; call `cocos_2x_operation_reconcile` only when its recovery preconditions are satisfied. Do not repeat a possibly completed write. Record visual acceptance with `cocos_2x_operation_preview_accept` only after inspecting the matching operation in the local Web preview; use the exact observed URL, observation time, and a concise description. If automatic runtime readback already passed, the visual receipt is appended to that preview phase without replacing the runtime evidence. Repeating identical visual evidence is idempotent.

For content builds, follow [cocos2-content-build](../cocos2-content-build/SKILL.md): call `cocos_2x_content_build_plan`, proceed to `execute` only when ready, then read `get` and require a verified completed package. Use `reconcile` for an interrupted build record without relaunching Creator. For a runtime preview, call `cocos_2x_content_preview_start` only for that completed build, open the returned loopback URL when visual/runtime observation is needed, inspect `get` for the application receipt, then call `stop`. A preview session lives only while this MCP process remains open.

For PNG resources that need to become scene objects, call `cocos_2x_assets_scene_plan` first and inspect the target scene, source identities, positions, and returned `pipelineId`. Execute with that exact ID and matching sources, then inspect `get` and `validate`. Open the matching local Web preview and inspect every Sprite before calling `preview_accept` for each returned `operationId`. Use `compensate` when the result must be undone; it removes the scene references before it attempts AssetDB deletion. Call `repair` only for an asset reported as `repairable`; it only refreshes the stale AssetDB mapping and verifies the UUID again.

When supported by the MCP client, request progress notifications for `assets_scene_execute`. The 2.4 MCP adapter reports each Host command start/completion for this operation. While it runs, repeated execution returns `PIPELINE_EXECUTION_IN_PROGRESS`, and other non-read-only calls for that project return `EDITOR_BUSY`; use `assets_scene_get` to inspect the receipt. A client timeout or disconnect does not cancel the Worker or establish that a write failed. Read the pipeline and operation records before choosing compensation; never blindly retry. Progress notifications may not extend a particular client's request timeout.

Call `cocos_2x_assets_scene_cancel` only when the user explicitly asks to cancel an active pipeline. It waits for the current Creator Host command to finish, then stops before a later write and attempts to compensate this pipeline's scene nodes before deleting its own imported assets. Read `assets_scene_get` afterward and treat `needs-review` as unresolved; a cancellation request is not proof that rollback completed.

If `assets_scene_execute` times out or returns an uncertain result, do not call `execute` again blindly. Read the pipeline and child scene batch, query each exact node path with `cocos_2x_command_execute(scene.node.inspect)`, and inspect the operation record. Compensation may reconcile a missing operation record only after the selected Creator instance and Canvas identity still match, the imported asset SHA/UUID still match, the exact node is absent from the live scene, and the serialized scene readback confirms the same parent and no target child. An apply reconciled as `WRITE_RECONCILED_NO_EFFECT` is rejected and is not retried automatically; compensate the other applied items and then verify AssetDB files, `.meta` files, scene references, and the final pipeline receipt. If any of those checks is incomplete, leave the pipeline in `needs-review`.

After the pipeline reaches `completed`, use `cocos_2x_content_from_scene_plan` to derive a release. Choose stable asset IDs, list dependencies, name the entry PNG, and inspect the returned manifest and fingerprint. Call `content_from_scene_stage` only after reviewing that plan. Read the existing pointer with `content_get`, then select using `content_select` with the exact `expectedCurrent` value. Selection changes Host metadata; it does not prove runtime application. Build the selected fingerprint with `content_build_plan/execute`, start its runtime preview, and require `content_preview_get` to report an accepted runtime receipt. Use `content_rollback` with the current release ID if the runtime result is not acceptable, then inspect the preview receipt again.

**Validation status:** the official MCP TypeScript SDK client connected to a real stdio MCP server and Creator 2.4.15. It discovered 14 tools, selected the ready `helloworld` instance, read eight available commands, and completed a temporary `scene.node.create` write, disk/runtime readback, visible preview, visual receipt append, compensation, and replay. Final `operation.get`/`scene.node.inspect` confirmed completed compensation with the probe absent. A synthetic uncertain-write record was reconciled through MCP against the real active scene and disk; both showed no effect and the fixture was removed. MCP `content.build.plan/execute/get` returned `ready/verified/completed` for a new isolated Web-Mobile build, and that same build passed MCP preview start/get/stop. The browser showed the blue square over the Cocos logo and Hello World; `get` returned `runtime-observed` with an applied runtime receipt. The preview service and browser tab were closed, and the short-lived URL token was redacted from the trace. A temporary synthetic `running` build record referencing that verified output was then reconciled through the actual MCP stdio process: the result was `verified`, `get` read back `completed`, and retry returned `already-terminal`; the fixture was deleted. This validates the adapter and idempotent terminal behavior, not recovery after a real Host crash.

Thirteen resource-pipeline and content-release MCP tools now map to the existing 2.4 Host contract; InMemoryTransport tests cover discovery, schemas, fixed target construction, and each route. A separate actual MCP stdio run against an isolated temporary project validated `content.get/select/rollback`, stale compare-and-set rejection, and selection restoration; the synthetic project was deleted. A live MCP instance query could not reach the real Creator catalog because macOS was locked (`CATALOG_FAILED`), so no asset import, scene write, or `content.fromScene.plan/stage` operation was attempted through this adapter. The Host/Creator resource pipeline and release flow have prior independent Web-preview acceptance, but that does not establish live acceptance through these MCP tools. The sample `.fire` file was restored to the committed version after Creator rewrote serialization fields. See the [MCP acceptance trace](../../traces/cocos-agent-mcp-2.4.jsonl).

The adapter also serves the fixed `cocos://2x/agent/mcp-tools` Resource and the `cocos_2x_resource_to_scene_workflow` Prompt. InMemoryTransport coverage verifies resource discovery/read, prompt discovery/expansion, selected-project scoping, and the no-blind-retry and visual-evidence instructions. A real `StdioClientTransport` session also listed/read the Resource and listed/expanded the Prompt with a registered project; it did not query Creator or invoke a model. These MCP capabilities provide guidance only; they do not substitute for live Creator or preview validation.

The resource-to-scene `execute` path now runs in a Worker and can emit MCP progress notifications around Host calls. Tests cover the Worker message path, progress-token forwarding, duplicate-execution rejection, status reads while busy, explicit cooperative cancellation, and simulated compensation of scene nodes/assets at safe boundaries. These new progress/cancellation paths have not yet been exercised against a live Creator write; host timing, client-specific timeout behavior, and live compensation remain unverified.

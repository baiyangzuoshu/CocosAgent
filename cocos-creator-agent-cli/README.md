# Cocos Creator Agent CLI

Standalone local CLI for Cocos Creator 2.4.1–2.4.16 projects. When choosing an installed editor automatically, it prefers the highest supported patch in descending order (2.4.16, 2.4.15, …, 2.4.1); an explicit `--creator` path takes precedence. It can run without Codex, Claude Code, Cursor, VS Code, DeepSeek Harness, or the retired Creator-native CocosAgent. The package owns the stdio MCP server, Codex/Claude native-command and Cursor/VS Code JSON MCP setup, DeepSeek Harness Cordis profile integration, bundled Creator Skills and installer, loopback bridge, Creator project extension template, and canonical Creator command contract.

## Requirements

The current source package version is 1.0.0; it has not been published yet and has no matching release tag. The latest published GitHub Release is 0.11.1. On macOS, `creator installations` discovers Creator `.app` bundles in the standard Cocos install locations; `project open`, `creator build`, and `creator compile` select the highest installed supported patch when `--creator` is omitted. Opening waits by default for a live extension handshake and a successful `creator.project.info` round trip, so `editorReady: true` confirms the selected path and Creator version answered from the editor. It reuses an already-open supported instance for the project and reports ambiguous or incompatible instances without launching another copy. After a readiness timeout, macOS Accessibility is queried for Creator modal dialogs; if permission or the query is unavailable, the result says so rather than guessing. The bundled Creator extension is 0.8.127. `creator.scene.ui.inspect` reads bounded typed properties for Button, Toggle, ToggleContainer, Slider, ScrollView, PageView, EditBox, LabelOutline, LabelShadow, ToggleGroup, SafeArea, and SubContextView, and current event lists for Button, Toggle, ToggleContainer, Slider, ScrollView, PageView, and EditBox. `ToggleGroup.toggleItems` is read-only; SafeArea has no component-specific Inspector fields beyond the shared `enabled` control. Newly added component inspection and runtime behavior require per-component Creator 2.4.15 acceptance. `creator.scene.ui-events.set.plan/commit/reconcile` replaces event lists on those components with exact target/handler checks and serialized `.fire` readback; `creator.scene.ui-events.set.compensate.plan/commit/reconcile` derives the original list from one completed operation and restores it without accepting caller-selected events. The Button-specific command remains available for compatibility. Scene preview numeric component assertions support bounded tolerances and read Creator 2.4 `cc.Slider.progress`, `cc.ProgressBar.progress`, and `cc.Sprite.fillRange` through their verified serialized storage fields. Existing scene nodes support planned transform, active-state, rename, reparent, component-property, component-addition, component-removal, and subtree-deletion changes, alongside AssetDB-backed asset operations, all with precondition checks and disk readback recovery. Scene composition can instantiate an exact AssetDB Prefab as a new scene node; `creator.prefab.source.inspect` reads the exact saved Prefab and `.meta` by AssetDB UUID and reports node/component identities and serialized fields, while `creator.prefab.source.editable.inspect` reads public Inspector properties and UI event lists through Creator Prefab edit mode and exits without saving. `creator.prefab.instance.inspect` reads the exact live scene instance, its linked Prefab root and bounded descendant links, plus saved scene/Prefab hashes. `creator.prefab.instance.override.plan/commit/reconcile` invoke Creator's native Apply or Revert action on the explicit commit call and bind the exact live instance state plus saved scene/Prefab hashes. They report an observed effect only after the expected AssetDB file changes are read back; they do not claim component-by-component override equivalence and must be accepted in Creator 2.4.15. `creator.prefab.source.patch.plan/commit/reconcile` bind declared public Inspector-serializable component fields to saved component identity and serialization keys, plus supported node fields, same-parent sibling ordering, bounded in-Prefab reparenting, leaf-child insertion/removal, and a componentless subtree insertion capped at 16 nodes/depth 4. Subtree removal is available only as source-linked compensation of that exact insertion. One registered built-in or project script component may be appended with compensation removal of that exact new instance; inherited Creator disallowMultiple families and required-component constraints are rejected during preflight; custom-script constructors and lifecycle hooks may execute in Creator. Direct removal is limited to a final registered built-in `cc.*` component when its enabled state, stable or synthetic identity, and declared Inspector-serializable properties of supported scalar/vector/color/rect/size types are captured, it has no unresolved UI event lists or dependent components, and every restored value can be applied or read back through Creator. Unsafe references, arrays, unsupported property types, dependencies, and non-final components are rejected. Creator 2.4.15 Tank apply/compensate/reopen acceptance covers `cc.BlockInputEvents.enabled` and `cc.ToggleGroup.allowSwitchOff`; other component classes and property types still need separate acceptance. See the [Prefab component removal acceptance trace](../../docs/agent-foundation/traces/cocos-creator-cli-prefab-component-removal-acceptance-20261024.md). Creator save, edit-mode exit/reopen, and saved-file readback verify writes. Prefab UI event-list patching is implemented for Button, Toggle, ToggleContainer, Slider, ScrollView, PageView, and EditBox; event targets and one exact handler must resolve inside the same Prefab. Creator 2.4.15 Tank acceptance has passed apply, full-project CLI close/reopen readback, and source-linked compensation for a two-node `node.subtree` insertion, a `cc.Button` appended to the inserted child, its public `zoomScale` property, and its `clickEvents` handler; the fixture was then removed and both the Prefab and scene returned to their recorded source hashes. Direct Prefab edit-mode node targeting is used for component property reads and writes so it does not depend on scene-tree lookup. Existing acceptance also covers `cc.Button.clickEvents`, same-parent `node.siblingIndex`, in-Prefab `node.parent`, empty leaf `node.child`, and `component.structure`. See [`cocos-cli-prefab-subtree-acceptance-20261024.md`](../../docs/agent-foundation/traces/cocos-creator-cli-prefab-subtree-acceptance-20261024.md) for operation IDs and exact evidence. `creator.editor.eval` and `creator.editor.eval-file` add bounded execution on explicit commit calls for inline scripts or exact project `packages/*/editor-scripts/*.js` files; scripts run with Creator `Editor` privileges and are not sandboxed. Their results do not verify arbitrary effects or persistence, and reconciliation never reruns them. Every supported scene-node write confirms persistence only after rereading exact AssetDB files and checking planned state. `vcs status` adds a read-only Git summary grouped by scenes, Prefabs, scripts, assets, metadata, project settings, and other files, including `.meta` pairing hints.

- Node.js 20 or newer.
- Cocos Creator 2.4.1–2.4.16 for editor-connected commands. Real-editor acceptance evidence currently covers 2.4.15 only.

Creator write and control commands execute immediately when their commit tool is called; no Creator approval dialog appears. MCP marks write/control tools as destructive. Codex assesses the exact plan or code and tells the user about material risks before invocation. The extension still verifies project identity and write preconditions, confirms results through readback where supported, and never retries uncertain writes automatically.

## Install and update

The CLI distribution channel is a versioned GitHub Release tarball, not the public npm registry. The first matching Release must be published before these commands work. Install an exact release globally with:

```sh
VERSION="0.11.1"
npm install --global "https://github.com/baiyangzuoshu/CocosAgent/releases/download/cocos-creator-agent-cli-v${VERSION}/cocos-creator-agent-cli-v${VERSION}.tgz"
```

The install example is pinned to the latest published release, `0.11.1`. The source package version `1.0.0` is not installable from GitHub Releases until its matching tag has been published.

Check for or install the latest release from the terminal:

```sh
cocos-creator-agent self-update --check
cocos-creator-agent self-update
```

Pin or roll back to a specific release with `cocos-creator-agent self-update --version <VERSION>`. Updates download the release archive and its SHA-256 asset, verify the checksum, then ask npm to replace the global package. Verify the installed package with `cocos-creator-agent version --format json`.

For a private GitHub repository, the updater reads `GH_TOKEN` or `GITHUB_TOKEN`, then falls back to `gh auth token --hostname github.com`. The token is sent only to `api.github.com`; authenticated asset downloads use GitHub's release-asset API and follow its signed download redirect. Never put the token on the command line.

Repository maintainers publish a CLI release by updating `package.json`, committing the change, and pushing a matching `cocos-creator-agent-cli-v<VERSION>` tag. The GitHub Actions workflow checks the tag against the package version, creates an npm tarball, and attaches the archive and SHA-256 file to the GitHub Release. Bump `creator-extension/package.json` whenever its installed behavior or contract changes; extension updates use the template bundled in the installed CLI.

`doctor` is read-only and does not start the bridge. It checks the Node.js and bundled contract versions, bridge health, connected Creator instances, and—when `--project-root` is supplied—the project extension and path identity.

`vcs doctor` is a separate read-only Git/filesystem diagnostic. It requires the exact Git repository root and a Creator project root inside it; it does not stage, rewrite, or restore files. It reports tracked `library/`, `temp/`, `local/`, or `build/` paths, missing or orphaned asset `.meta` sidecars, duplicate main/subasset UUIDs parsed from JSON metadata, and paired Git conflict markers in bounded text files. Findings are diagnostic evidence, not an AssetDB import receipt; symlinks are not followed and scan limits are included in the JSON result.

`vcs status --git-root <absolute-path> --project-root <absolute-path>` reads Git's working-tree and index status, then groups changes by Cocos scenes, Prefabs, scripts, assets, metadata, project settings, and other files. It includes branch/upstream counts, staged versus unstaged state, changes outside the selected Creator project, and missing/orphaned `.meta` pairing hints for changed assets. It is read-only; `vcs doctor` remains the full project integrity scan.

`vcs impact --git-root <absolute-path> --project-root <absolute-path> [--target <ref>] [--operation switch|sync]` compares the current local `HEAD` tree with a local branch, commit, or (by default) configured upstream. It reports incoming project files, possible AssetDB reimports, `.meta` identity review, script recompiles, scene/Prefab reloads, project-version compatibility, and dirty paths that overlap incoming files or their metadata pairs. `--operation sync` also reports whether the local target permits a fast-forward. It never fetches, switches, merges, or writes Git state, and does not connect to Creator; verify project identity in Dashboard and close/reload the Editor before applying the change. A path-based classification is an impact estimate, not an AssetDB import or runtime receipt.

`vcs diff --git-root <absolute-path> --project-root <absolute-path> --path assets/Scenes/Level.fire [--from <revision>] [--to <revision>]` compares a Creator 2.4.15 `.fire` scene or `.prefab` between Git revisions or from `HEAD` to the working tree. It matches nodes by serialized UUID and reports hierarchy, transforms, component additions/removals, and serialized component property changes. Linked Prefab scene changes stay attributed to the instance node; the command does not infer which source Prefab field caused an override. The command reads Git blobs and regular project files only, and rejects unsupported asset identity, malformed serialization, symlink paths, and oversized files.

`vcs blame --git-root <absolute-path> --project-root <absolute-path> --path assets/Scenes/Level.fire --node <node-uuid> [--revision <revision>] [--max-commits 128]` finds the newest first-parent commit that changed the selected serialized node UUID. It includes author, commit subject, and the semantic node/component change, and reports when the requested history limit was reached. It is read-only, refuses shallow clones, follows the asset path without rename tracking, and reports component changes with their owning node.

`vcs conflicts --git-root <absolute-path> --project-root <absolute-path>` reads unmerged Git index stages and explains Creator `.fire`/`.prefab` conflicts by node UUID. It compares base-to-ours and base-to-theirs changes, separates overlapping fields from disjoint or convergent changes, and reports metadata identity mismatches. `vcs conflicts resolve --git-root <absolute-path> --project-root <absolute-path> --path <project-relative-path> --side <ours|theirs>` previews selecting one exact Git side for a conflicted project file; `.fire`/`.prefab` files and a conflicted matching `.meta` are resolved together and checked for UUID identity. The command is read-only until `--apply` is supplied. Applying writes and stages the chosen bytes, then verifies Git index and working-tree readback; review the staged files before committing. It does not synthesize a field-level merge.

`instances list` also reports recent authenticated but incompatible extension handshakes under `rejectedInstances`, including the extension-reported project path and mismatch reasons. These diagnostic records have no command session or capabilities. `doctor` flags them as errors instead of reporting only zero instances.

`creator installations` reports discovered bundle paths, Creator versions, executable availability, and whether each installation is in the supported Creator 2.4.1–2.4.16 range. By default it scans `/Applications/Cocos/Creator`, `/Applications/CocosCreator`, their matching per-user `~/Applications` locations, and direct Cocos-named entries under `/Applications`; `--search-root` scans one additional absolute directory to depth two. Discovery is read-only and follows no symlinks. On unsupported platforms, use an explicit Creator path where its package format is supported.

On Windows, `creator installations` scans `C:\CocosCreator`, `C:\CocosDashboard\resources\.editors\Creator`, matching per-user locations, and an optional explicit `--search-root`. The scan looks for `CocosCreator.exe` and reads the Creator version from local package metadata, including Electron `resources/app.asar`; it is bounded to 5,000 directories per root and depth six. `project open`, `creator build`, and `creator compile` accept a Creator installation directory or executable path. Creator 2.4.1–2.4.16 discovery and launch are supported on macOS and Windows; Linux is reported as unsupported.

`project list` scans the default `~/Documents/CocosProjects`, `~/CocosProjects`, `~/Projects`, and `~/Documents` roots to depth three, or scans the supplied `--search-root` directories. It is a filesystem search rather than a read of Dashboard's private recent-project database; unsupported Creator versions are listed with `supported: false`. Symlink directories and Creator caches are skipped, and traversal is capped at 10,000 directories. `project clone` copies a local supported Creator 2.4.x project (2.4.1–2.4.16) to a new absolute path, preserves asset bytes and `.meta` UUIDs, assigns a new project ID and name, and omits `.git`, `node_modules`, and root Creator caches (`library/`, `temp/`, `local/`, `build/`). It refuses existing destinations, overlapping source/destination paths, and symlinks or special files. The clone is not opened automatically; verify its name, path, and Creator version in Dashboard before opening it.

`project templates list` reads local templates from the highest installed supported Creator patch, or from an explicit `--creator` / `--template-root`. `project create` copies one such template into a new path and preserves that template’s supported Creator patch in `project.json`, assigns a new project ID and name, and preserves template asset metadata. It does not fetch online templates or open the created project. `project clone` performs the same copy safeguards on an existing supported local Creator 2.4.x project.

`project open` first validates the absolute project path and that `project.json` declares Creator 2.4.1–2.4.16. Before it opens or switches a project, verify the project name, absolute path, Creator version, and current open state in Cocos Dashboard. Pass `--creator` to select an exact macOS Creator `.app` or Windows installation/executable; if omitted, the CLI selects the highest installed supported patch (2.4.16 down to 2.4.1), failing when no supported installation exists or the preferred version has duplicate installations. By default, it reuses an existing supported instance; if an explicit `--creator` patch differs from that instance, it refuses instead of switching the open editor. When no supported instance is open, it launches the highest installed patch unless `--creator` was supplied, and waits up to 120 seconds for the extension handshake plus a read-only `creator.project.info` response whose project path and Creator version match. On timeout, it uses the Creator process ID from the extension handshake (or the launched process ID) to query macOS Accessibility for `AXDialog`/`AXSheet` windows. The response distinguishes a detected modal dialog, no detected dialog, and a diagnostic that is unavailable; it never treats missing Accessibility permission as proof that no dialog exists. A timeout returns nonzero with `editorReady: false`. Use `--no-wait-ready` only when you need the earlier process-launch behavior. `--format json` returns structured errors on stdout for machine callers.

`project close --instance <id>` targets one exact supported Creator 2.4.x process. A connected instance follows Creator's `File > Open Project...` close flow. If the selected instance is rejected only because its extension version or command contract is stale, the CLI validates the reported project path and Creator executable, requests a normal application quit, and waits for both process exit and bridge disconnect. The default timeout is 60 seconds so the bridge's 45-second heartbeat expiry can settle after Creator exits. macOS uses System Events; Windows sends a normal window-close request. Creator handles any save prompt, and the CLI never force-kills the process. If the process exits while the bridge still reports the instance connected, the CLI returns `closed: false` with that mismatch instead of reporting a false success. If Creator remains open, the result reports the modal-dialog diagnosis when available and leaves the process untouched. Linux is unsupported. The Windows route is covered by mocked contract tests and still needs Windows Editor acceptance.

Use `cocos-creator-agent help <command> [<subcommand>]` or append `--help` to a command to show focused usage; `help search <query>` searches CLI usage and the Creator command catalog. Machine callers can use `--json` or `--format json` on errors. Error objects include `schemaVersion`, stable `error.code`, `error.kind`, and `exitCode`. Exit codes are `1` for general failures, `2` for usage or input errors, `3` for bridge/MCP connection failures, `4` for Creator/project/build workflow failures, `5` for write conflicts or required reconciliation, and `10` when a Creator preview or project test fails.

### Component-property compensation

`creator.scene.node.set-component-property.compensate.plan` takes a completed source `operationId` and derives the restore value from that source. It refuses live or saved state drift and reserves one compensation per source; the caller cannot substitute another restore value. Commit the returned compensation plan explicitly, then use its operation ID to reconcile an interrupted write.

## MCP and Agent Skills

The CLI starts its own stdio MCP server with `cocos-creator-agent mcp serve`. It advertises MCP `tools.listChanged` and, after the first tool listing, checks the CLI command catalog and connected Creator project-tool registries every 15 seconds by default. A changed tool schema or set emits `notifications/tools/list_changed`; clients then request `tools/list` to load the new definitions. Set `COCOS_MCP_TOOL_REFRESH_INTERVAL_MS` from 1000 to 300000 to tune the polling interval. The server exposes read-only GitHub Actions workflow, run, job, and artifact tools, plus explicitly annotated workflow dispatch and run cancellation operations. Use `mcp configure codex` or `mcp configure claude-code` to register through their native CLIs. Cursor and VS Code use their standard JSON formats: `~/.cursor/mcp.json` or `.cursor/mcp.json`, and the VS Code user profile or `.vscode/mcp.json`. DeepSeek Harness uses the selected profile's `cordis.patch.yml`; `mcp configure deepseek-harness --profile web` adds a marked `@deepseek-ai/dsh-mcp-client` stdio entry (default profile: `web`). Set `--dsh-home <path>` for a custom Harness home. The adapter changes only its marked block, preserves other patch content, writes atomically, and refuses symlink paths or a modified managed block unless `--force` is supplied. Use `mcp status deepseek-harness [--profile <name>]`, `mcp list`, and `mcp remove deepseek-harness [--profile <name>]` to inspect or remove it. `--local` is not supported for DeepSeek Harness MCP configuration. Reload the Harness profile after setup.

The npm release bundles all Creator workflow Skills and Creator 2.4.15 reference notes. `skill show [name]` reads the bundled instructions without installing them; `skill show --list` lists them. `skill install <client>` installs all bundled Skills into Codex `~/.codex/skills/`, Claude Code `~/.claude/skills/`, or DeepSeek Harness `$DSH_HOME/skills/` (default `~/.dsh/skills/`). Use `--dsh-home <path>` for a custom Harness home. `--local` uses `.agents/skills/` for Codex or `.claude/skills/` for Claude Code; DeepSeek Harness local/project Skill installation is not exposed. Use `--skill <name>` to select one, `--dry-run` to preview, and `skill refresh <client>` to update previously managed copies. The installer preserves unrelated files, detects edits, and refuses unmanaged or modified targets by default. `--force` backs up the replaced directory under `~/.cocos-creator-agent/skill-backups/`. Reference notes are installed beside the client skill directory so relative links continue to resolve.

Use `instances list` to discover an editor instance, then pass its exact ID to `capabilities` or `call`. The Creator catalog includes read commands and script-asset write workflows:

1. Call `creator.script.create.plan` with an existing `assets/` subfolder, an `assets/`-relative JS/TS path, and exact source. Creator verifies that the parent path has no symlinks and the file and `.meta` are absent, then stores a private operation record under `~/.cocos-creator-agent/creator-operations/` and returns an operation ID, plan hash, source preview, and recovery conditions. It does not change project assets or create folders.
2. After reviewing that plan, call `creator.script.create.commit` with only its operation ID and plan hash. The explicit commit call authorizes only this operation; no Creator dialog opens. The extension performs a fresh project/version/path/absence/hash check, then creates the asset through `Editor.assetdb.create`.
3. The extension reads the created script and `.meta` back through the same Creator instance and returns the UUID, importer, source hash, metadata hash, and conditional recovery data. If the response is lost or the bridge restarts, call `creator.script.create.reconcile` with the original operation ID. Writes are never automatically retried; a changed target is reported as a conflict.

For an existing asset, read it first and pass its exact `sourceSha256` to `creator.script.modify.plan` with the complete replacement source. The plan binds the asset path, AssetDB UUID/importer, source and `.meta` hashes, and stores the prior source outside the project. The explicit commit call requires the operation ID and plan hash; it rechecks all preconditions immediately before writing through `Editor.assetdb.saveExists`, then reads the source and AssetDB identity back. `.meta` is preserved. On uncertainty, call `creator.script.modify.reconcile`; never replay the write. After modification, `creator.script.recompile.plan` binds a follow-up AssetDB refresh to the exact script UUID, source hash, importer, and `.meta` hash. Its commit call invokes Creator's documented `Editor.assetdb.refresh` and returns `passed` only when the callback includes that exact script and no `asset-db:script-import-failed` event was observed. An import failure is returned with diagnostics; an empty/ambiguous refresh result stays `unconfirmed`. The operation never edits source and never reruns during reconciliation.

The scene-node read command can inspect one node by scene UUID and node UUID even when it is outside the bounded snapshot. `creator.scene.compose.plan` prepares up to 32 new nodes (depth 6), 64 registered components, typed scalar/asset/exact node or component reference properties, and up to 32 UI event-list bindings (12 entries per list) as one operation. Optional `anchorX` and `anchorY` extend the legacy transform fields. Existing `buttonEvents` remains supported; `uiEvents` binds the 12 whitelisted event properties across Button, Toggle, ToggleContainer, Slider, ScrollView, PageView, and EditBox. Existing nodes can serve as parents, exact property references, or event targets, but the operation does not mutate them. A node may specify `prefabUuid` to instantiate that exact AssetDB Prefab; its root transform must still provide all eight legacy transform fields, and the operation does not add components or bind events on the Prefab root. cocos-creator-agent call --instance <instance-id> --command creator.scene.node.remove-component.plan --input '{"sceneUuid":"<scene-uuid>","nodeUuid":"<node-uuid>","componentClassName":"cc.Sprite","componentInstanceId":"<component-instance-id>"}'
```sh
cocos-creator-agent call --instance <instance-id> --command creator.scene.node.remove-component.commit --input '{"operationId":"<operation-id>","planHash":"<plan-sha256>"}'
cocos-creator-agent call --instance <instance-id> --command creator.scene.node.remove-component.reconcile --input '{"operationId":"<operation-id>"}'
```

For a new Button and handler, have the plan allocate stable Creator UUIDs for nodes created by the operation. Existing nodes are referenced as `uuid:<creator-uuid>`; nodes in the plan use `new:<id>`:

```sh
cocos-creator-agent call --instance <instance-id> --command creator.scene.compose.plan --input '{"sceneUuid":"<scene-uuid>","nodes":[{"id":"button","name":"StartButton","parentRef":"uuid:<canvas-uuid>","transform":{"x":0,"y":0,"width":180,"height":64}}],"components":[{"id":"button-ui","nodeRef":"new:button","className":"cc.Button","properties":[]},{"id":"handler","nodeRef":"new:button","className":"ButtonState","properties":[]}],"buttonEvents":[{"buttonRef":"new:button","handlerRef":"new:button","handlerComponentClassName":"ButtonState","handler":"onClick","customEventData":"toggle"}]}'
cocos-creator-agent call --instance <instance-id> --command creator.scene.compose.commit --input '{"operationId":"<operation-id>","planHash":"<plan-sha256>"}'
cocos-creator-agent call --instance <instance-id> --command creator.scene.compose.reconcile --input '{"operationId":"<operation-id>"}'
```

The new node UUID is returned in the plan and remains stable through commit and reconciliation. Add an asset-backed component property using `{ "assetUuid": "<asset-uuid>", "assetClass": "SpriteFrame" }` as its value; only the documented asset-class enum and a property whose Creator type matches that class are accepted.

To add a component, use its exact Creator class name (for example `cc.Sprite`) and follow the same plan/commit/reconcile sequence:

```sh
cocos-creator-agent call --instance <instance-id> --command creator.scene.node.add-component.plan --input '{"sceneUuid":"<scene-uuid>","nodeUuid":"<node-uuid>","componentClassName":"cc.Sprite"}'
cocos-creator-agent call --instance <instance-id> --command creator.scene.node.add-component.commit --input '{"operationId":"<operation-id>","planHash":"<plan-sha256>"}'
cocos-creator-agent call --instance <instance-id> --command creator.scene.node.add-component.reconcile --input '{"operationId":"<operation-id>"}'
cocos-creator-agent call --instance <instance-id> --command creator.scene.node.set-component-property.plan --input '{"sceneUuid":"<scene-uuid>","nodeUuid":"<node-uuid>","componentClassName":"cc.Label","componentInstanceId":"<component-instance-id>","property":"string","value":"Ready"}'
cocos-creator-agent call --instance <instance-id> --command creator.scene.node.set-component-property.commit --input '{"operationId":"<operation-id>","planHash":"<plan-sha256>"}'
cocos-creator-agent call --instance <instance-id> --command creator.scene.node.set-component-property.reconcile --input '{"operationId":"<operation-id>"}'
cocos-creator-agent call --instance <instance-id> --command creator.scene.node.set-component-property.compensate.plan --input '{"sourceOperationId":"<completed-operation-id>"}'
cocos-creator-agent call --instance <instance-id> --command creator.scene.node.set-component-property.compensate.commit --input '{"operationId":"<compensation-operation-id>","planHash":"<plan-sha256>"}'
cocos-creator-agent call --instance <instance-id> --command creator.scene.node.set-component-property.compensate.reconcile --input '{"operationId":"<compensation-operation-id>"}'
```

Component-property compensation derives the restore value from one exact completed source operation; it accepts no caller-provided replacement value, refuses live or saved state drift, and reserves at most one compensation operation for that source.

UI event-list compensation uses the same source-operation binding. It restores the exact prior event list, rejects caller-supplied replacement events, and can reconcile the completed compensation after a Creator restart against the exact live component and saved `.fire` state.

After Creator restarts, the source-linked compensation reconcile command may verify the operation against the current live component identity and the exact saved `.fire` state. It never replays a mutation. Ordinary component-property operations still require manual review when their Creator session changes.

For a component property declared as `cc.Node`, use `{ "kind": "node-ref", "nodeUuid": "<target-node-uuid>" }`. For a declared component reference, pass `{ "kind": "component-ref", "nodeUuid": "<target-node-uuid>", "componentClassName": "game.Controller", "componentInstanceId": "<current-component-instance-id>" }`. The target must be in the active scene, and the component instance ID is session-specific. Typed object arrays such as `type: [cc.Vec2]` accept bounded `kind: "array"` items. Declared arrays of supported asset, node, or component references are also accepted when each item matches Creator's declared element type; arbitrary object arrays remain unsupported.

`catalog --format json` and `call --instance <id> --command <id> --input <json> --format json` are the machine-readable interface used by the CLI-owned MCP server. MCP exposes the plan/commit/reconcile tools for scene composition, script modification and recompile, AssetDB import, and Prefab creation; `cocos_scene_diff` compares two bounded Creator snapshots without reading arbitrary files.

Project-local extensions can publish declarative Creator command providers. The CLI discovers them from the live editor, validates the provider fingerprint and input schema, and exposes them as project-scoped MCP tools. See [`references/2x/13-agent-command-providers.md`](references/2x/13-agent-command-providers.md) for the contract. Providers run as Creator main-process extension code and are not sandboxed; write/control commands execute immediately when called, without a Creator dialog.

## Project test plans

Project test plans are documented in [`references/2x/14-project-test-runner.md`](references/2x/14-project-test-runner.md). Use `creator test --project-root <absolute-path> --list` to inspect the plan; running it writes separate JSON/JUnit reports. `creator watch --project-root <path> --paths '["tests","assets/Scripts"]' --affected` watches files/directories and reruns affected suites. Node suites use actual Node test subprocesses; editor suites invoke the selected project Creator Provider or Editor script; preview suites use the exact supplied preview session and can run project-local scripts against the live `cc` runtime. Preview test scripts are not sandboxed; uncertain execution closes the Agent-owned browser and stops watch for manual review.

## Project tool registrations

A project may add `.cocos-agent/tools.json` to register named aliases for commands already present in the shared Creator contract. Read and plan commands can be exposed directly; write or control commands execute immediately when the canonical command is explicitly invoked. The registry cannot run project callbacks or change a command input schema. MCP ignores project-provided titles and descriptions when publishing tool definitions, and write aliases retain destructive annotations so Codex can assess their risk before invocation. The registry is re-read from the selected live Creator project for listing and invocation; calls include its SHA-256 so edits invalidate stale tool discovery.

```json
{
  "schemaVersion": 1,
  "tools": [
    {
      "id": "player-script",
      "title": "Read player script",
      "description": "Read the player's component script and Creator metadata identity.",
      "commandId": "creator.script.read"
    }
  ]
}
```

Use `project-tools list --instance <id>` to discover the declarations and `project-tools call --instance <id> --tool player-script --input '{"scriptPath":"assets/Scripts/Player.ts"}'` to invoke one. Aliases use the mapped built-in command's exact input schema, access level, and live Creator capability; write/control calls execute immediately. Pass `--registry-hash <sha256>` when invoking a tool discovered earlier; the call is rejected if the project declaration changed. This is declarative routing over canonical commands, not an arbitrary Editor code execution API.

## Asynchronous tasks and recovery

`tasks start` returns a durable task ID without waiting for the Creator operation. `tasks wait --id <id> --after-sequence <N> [--wait-ms 25000]` holds a local bridge request until a newer persisted event arrives or returns the current progress on timeout. The response includes `eventSequence`; pass that cursor to wait for the next update. `tasks list` returns bounded summaries and `tasks status` reads one task's result; global `tasks list` works while Creator is disconnected, and `--instance <id>` filters it. `tasks cancel` requests cooperative cancellation. Task records are stored under `~/.cocos-creator-agent/tasks/` with restrictive permissions and contain the exact input for explicit recovery, while status output omits the raw input and reports its SHA-256.

After a bridge restart, queued tasks become interrupted; dispatched reads can be explicitly resumed. A dispatched script-creation commit resumes through `creator.script.create.reconcile`; scene-node transform, rename, reparent, deletion, component add/removal, active-state, and property commits resume through their matching `creator.scene.node.*.reconcile` command, each with its original operation ID and never by replaying the write. Other dispatched plans, writes, and controls become `needs-reconciliation` and are not replayed automatically. Cancellation is best effort after dispatch; a potentially side-effecting command may require reconciliation even when cancellation was requested.

## Compile and Web preview feedback

`diagnostics read --instance <id>` reads Creator Builder compile events, script-import failures, and editor Console events with a sequence cursor. A `compile-finished` event proves only that the event fired; it is not by itself a successful compile result.

`preview start --instance <id> [--port 7456]` requests Creator's active-scene Web preview immediately when invoked; Codex assesses the effects of running project code and informs the user about material risks before starting it. Creator's selected preview target must be Browser; the documented IPC follows that selection. Creator opens its normal preview, then the local bridge opens an isolated Chromium session to the same loopback port. The command returns a `previewSessionId` bound to that Creator instance, project, and scene UUID. Select Chromium with `COCOS_CREATOR_AGENT_BROWSER` when it is not in a standard install location.

Use that session ID with `preview observe`, `preview screenshot`, `preview refresh`, `preview interact`, and `preview stop`. Interactions include a keyboard whitelist, normalized canvas clicks and drags, bounded text insertion into the focused control, and exact-path `cc.Widget.updateAlignment()` or `cc.Layout.updateLayout()` refreshes; declarative assertions can verify scene/node/Console/component fields and UI geometry. Numeric component-property assertions may set a bounded tolerance (0–100) for runtime-computed float values such as Slider progress. Refresh reuses the same browser session and verifies the expected scene again. Screenshots are saved under `~/.cocos-creator-agent/captures/`; stopping closes the Agent-owned browser but leaves Creator's preview server running.

The runtime browser commands fail closed when Chromium, the loopback preview server, or the expected scene identity is unavailable. Runtime evidence is not inferred from source code or from Creator compile events.

## Player runtime command Providers

`runtime sessions list` lists active CLI-owned Web Preview sessions. `runtime commands list --session <id>` returns the game-side command catalog. To add a Provider, copy the packaged `runtime/provider.js` helper into the project's `assets/` directory, require it from a game script, and register a bounded command catalog:

```js
const runtime = require('./AgentRuntime/provider');
const gameState = require('./GameState');

runtime.registerProvider({
  providerId: 'game-state',
  protocolVersion: '1',
  commands: [{
    id: 'get-score', title: 'Read score', description: 'Read the current score.',
    access: 'read',
    input: { type: 'object', properties: {}, additionalProperties: false },
  }],
}, {
  'get-score': function () { return { score: gameState.score }; },
});
```

Invoke a listed command with its exact provider fingerprint and a schema-validated JSON object:

```sh
cocos-creator-agent runtime command call --session <preview-session-id> \
  --provider game-state --command get-score --fingerprint <sha256> --input '{}'
```

The CLI re-discovers the Provider before each call and the helper compares the live declaration again immediately before dispatch. `write` and `control` commands must declare `approval: true`; MCP marks them destructive. Provider handlers execute in the game page without sandboxing. Timed-out calls return an uncertain result and are not retried. The runtime API is available only in Agent-owned Web Preview sessions; it does not attach to arbitrary browsers or native Players.

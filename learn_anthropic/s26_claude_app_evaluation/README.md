# 第 26 课：如何建立 Claude 应用的质量评估？

**目标：** 能把应用需求转成清晰的成功标准、一组代表性测试任务、适当的评分方式和可重复的复核流程。

## 本课问题

模型输出“看上去不错”是否足以说明应用已经达到上线要求？当应用会使用工具或连续执行多步任务时，只检查最后一条回答又会漏掉什么？

## 官方资料

- [Define success criteria and build evaluations](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests)：定义成功标准、构造任务样本、选择代码、人类或 LLM 评分方式。
- [Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)：Agent 评估中的任务、试次、评分器、轨迹、结果和评估运行器。
- [A statistical approach to model evaluations](https://www.anthropic.com/research/statistical-approach-to-model-evals)：比较模型评估时的样本波动、配对比较和统计分析建议。
- [Choosing the right model](https://platform.claude.com/docs/en/about-claude/models/choosing-a-model)：使用任务评估比较候选模型与性能、成本取舍。

核对日期：2026-11-10。评估阈值由应用风险、用户需要和业务条件决定；下面的例子用于说明方法，不是 Anthropic 的通用上线标准。

## 1. 先把“做好”写成可检查的标准

“回答要好”“要安全”“要快”都太宽泛，无法稳定判断是否达标。官方指南建议成功标准具体、可测、可实现且与应用目标相关；大多数应用需要同时衡量多个方面，而非依赖单一总分。[Define success criteria and build evaluations](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests)

| 评估维度 | 需要明确的问题 | 可能的测量方式 |
| --- | --- | --- |
| 任务正确性 | 关键结论或标签需要多准确？ | 准确率、精确率/召回率、F1、测试断言。 |
| 上下文与依据 | 回答是否使用给定资料，引用是否支持结论？ | 引用核对、逐项 rubric、人工抽查。 |
| 边缘情况 | 对空白、无关、过长、矛盾或含糊输入如何处理？ | 分类测试、拒答/澄清检查、错误严重度统计。 |
| 一致性与表达 | 相似请求的结论是否稳定？语气是否合适？ | 多轮/改写样本、等级量表或人工评审。 |
| 安全与隐私 | 是否遵守敏感信息和禁止行为边界？ | 定义违规类别并统计触发率、人工复核高风险案例。 |
| 运行指标 | 响应是否够快，费用是否可接受？ | 响应时长、超时率、每项任务成本或 Token 用量。 |

把目标写成可判断的门槛，例如：“在保留测试集上，退货分类 F1 不低于团队设定值；缺少政策依据时必须标记无法判断；回答引用须支持答案；响应时长和每项费用分别低于设定预算。”阈值应由负责产品的人结合容错成本定出，而不是先看模型分数再倒推标准。

## 2. 构造能代表实际使用的测试样本

评估任务应反映真实工作中的输入分布，也要覆盖容易失败的边缘情况。官方示例包括无关或不存在的数据、过长输入、不良或有害用户输入，以及人类也难以达成一致的含糊案例。[Define success criteria and build evaluations](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests)

每条任务可以包含：

- 真实或经过隐私处理的输入，以及必要的对话历史、文件或工具环境；
- 期望结果、可接受结果范围，或清楚的评分 rubric；
- 样本类别和难度标签，例如常见问题、缺少依据、冲突信息、越界请求；
- 评估运行所需的模型、提示词、工具配置和应用版本。

迭代用样本和最终对照样本应分开维护。用于调提示词的样本容易被反复适配；保留一组未参与日常调优的测试样本，有助于检查改动是否只对熟悉案例有效。样本不仅要数量够用，也要覆盖真实用户与高风险场景。人工标签分歧本身也是信号：先澄清标准，再评模型。

## 3. 让评分方式匹配问题

| 评分方式 | 适合情况 | 优点与限制 |
| --- | --- | --- |
| 代码评分 | 标签、字段格式、工具参数、数据库状态等有明确规则的结果。 | 快、稳定、可大规模运行；对开放式表达和细腻判断不够灵活。 |
| 人工评分 | 高风险或需要领域知识、语境判断的案例。 | 判断灵活、可发现定义遗漏；成本较高，需统一 rubric 并抽查评分者一致性。 |
| LLM 评分 | 风格、依据质量或复杂指令遵循等较难用简单规则检查的维度。 | 可扩展且灵活；需先验证评分器可靠性，使用明确 rubric 和固定输出尺度，并抽取样本人工核对。 |

优先选择对目标问题足够可靠、速度和规模也合适的评分方式。精确匹配适合只有唯一标签的分类任务；对多种自然语言答案都可能正确的开放问题，强行逐字匹配会误判。LLM 评分器应根据明确条目给出有限选项或量表；Anthropic 文档建议先测试评分器的可靠性再扩大使用。[Define success criteria and build evaluations](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests)

## 4. Agent 要同时评“过程”和“结果”

简单对话任务可将一次输入、一次输出和评分规则组成一个测试项。Agent 可能连续调用工具、修改环境状态并从中间结果继续行动，因此应把运行结果与过程记录一起纳入评估。

Anthropic 的 Agent 评估文章使用这些概念：**任务**是含有输入与成功条件的测试项；**试次**是一次运行；**评分器**检查一个或多个方面；**轨迹**记录整次运行的消息、工具调用和中间结果；**结果**是任务结束时环境中的实际状态；**评估运行器**负责运行任务、记录步骤、评分并汇总结果。[Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

例如，一个订票 Agent 最后说“订票成功”不代表预订真的存在。评估应检查应用或沙箱里的预订记录，也要检查是否使用了允许的工具、是否遵守确认步骤。对模型行为有随机性的任务，可以对同一任务运行多次，记录单任务成功率或 `pass@k` 等指标，而不是把一次成功当成稳定能力。轨迹与最终状态一起保存，能帮助定位错误发生在哪个步骤。

## 5. 建立可复查的迭代闭环

1. **定义目标：** 写清任务质量、边缘情况、风险、延迟和成本底线。
2. **整理测试集：** 覆盖常见输入和高价值边缘案例，记录标签来源与版本。
3. **实现评分器：** 简单规则先用代码；复杂判断用清晰 rubric，LLM 评分先与人工结果校准。
4. **跑基线：** 固定模型、提示词、工具和应用版本，记录各项分数、成本、时延和失败例子。
5. **逐项改动：** 每次调整模型、提示或工具流程后，重跑相同测试集，检查目标是否改善以及其他维度是否退化。
6. **复核与持续观察：** 对高风险项、评分器分歧和新型失败进行人工复核；上线后结合用户反馈、生产监控和回归评估更新样本。

对于候选模型比较，应尽量让输入样本、提示词、工具和评分标准一致，并记录每个候选的差异。Anthropic 的统计评估文章提醒，基准成绩可能受测试题抽样波动影响；样本有限、结果接近时，不宜把很小的平均分差当作确定性优势。[A statistical approach to model evaluations](https://www.anthropic.com/research/statistical-approach-to-model-evals)

## 练习：给客服知识问答建立一份评估

某客服应用根据退货政策回答用户，并引用提供的政策片段。它有时会收到无关、过长或缺少答案依据的问题。请提出至少三个成功标准、三类测试样本，以及每项最合适的评分方法。

**参考答案：** 成功标准可包括：答案与政策一致；引用支持结论；缺少依据时会说明无法从资料确认；响应时长和成本符合团队设定。样本可包括普通退货问题、政策中没有答案的问题，以及掺入无关背景或超长内容的问题。标签/字段格式可由代码评分，引用是否支持结论和模糊案例可用 rubric 评分，并对 LLM 评分器结果抽样人工复核。上线后把新出现的失败模式补进回归集。

## 本课结论

可靠评估不是给一条输出打分，而是把应用成功条件写清楚，用代表性任务和边缘案例验证，再选择合适的评分器并反复运行。对 Agent，除了最终文字，还要检查工具轨迹和环境状态；对模型、提示或工具的每次重要改动，都要和可复现的基线比较。
